# 验收与质量门禁

## 1. v0.1 最小闭环验收

对应 `04-启动执行清单.md`，全部满足才算通过：

- [ ] `composer install` 成功，path 仓库解析全部本地包
- [ ] `php packages/demo/run.php` 稳定运行 5 帧无错误
- [ ] Actor 移动后 AOI 反映新位置（每帧 query 结果正确）
- [ ] 事件回调触发（`player.moved` 每帧输出）
- [ ] World 只依赖 `Nythros\Contracts` 接口，不依赖具体类
- [ ] 7 个核心包（kernel / scheduler / entity / actor / event / aoi / world）各有最小测试

## 2. 后续阶段验收

各阶段按验收结果推进，不是按时间推进。

### 引擎核心

必须满足：

- [ ] Runtime Kernel 在 Workerman 事件循环上运行
- [ ] Network 接口落地，WebSocket / TCP 传输可用
- [ ] Protocol 管线跑通：Message → Serializer → Frame → Transport，编解码数据一致
- [ ] Security 接口接入：Authenticator / Session / Identity 边界清晰，未认证连接可处理
- [ ] 慢客户端可处理
- [ ] 7 核心 API 冻结，核心测试完善
- [ ] Benchmark 可重复，无明显内存泄漏
- [ ] 引擎与具体游戏业务解耦

### 框架

必须满足：

- [ ] 一条命令启动服务器
- [ ] 一条命令创建 Actor
- [ ] BaseActor / BasePlayer / BaseMonster / BaseNPC 可用
- [ ] Plugin 机制可加载官方插件
- [ ] 配置可覆盖
- [ ] 日志可查询
- [ ] 监控可查看
- [ ] Demo 可运行
- [ ] 文档可跟随完成

### 发布

必须满足：

- [ ] `composer create-project` 可安装
- [ ] Quick Start 可执行
- [ ] Demo 可复现
- [ ] CI 通过
- [ ] Release 可安装
- [ ] CHANGELOG 完整

## 3. 性能测试原则

不拍脑袋定指标。不写"3000 人必须 <50ms"这种拍脑袋结论。

每次 Benchmark 必须记录：

```text
测试机器
PHP 版本
Workerman 版本
CPU
RAM
连接数
Actor 数
Cell 数
Tick Rate
消息频率
广播数量
P95
P99
错误率
```

形成版本序列：

```text
Benchmark v0.1
Benchmark v0.2
Benchmark v0.3
...
```

只有版本序列可对比，才能判断每次修改是性能提升还是退化。

## 4. 质量门禁

以下任意一条触发，不得进入下一阶段：

1. 核心测试失败。
2. Benchmark 明显退化。
3. Actor 状态出现并发错误。
4. AOI 出现错误广播。
5. 集群消息丢失无法解释（进入集群阶段后适用）。

总原则：

> 线路图不是"时间到了就进入下一阶段"，而是"验收通过才进入下一阶段"。
