## 一、交付内容

### 1.1 归档读路径（blueprint/27 §五 遗留项）

| 模块 | 说明 |
|---|---|
| `ArchivePipeline::load`（framework） | 按 id 读最近归档记录（StorageInterface::load 本就存在，管线层补透传 + 异常吞并返回 null——恢复语义「尽力而为」，失败回落全新入场）。 |
| `MapServer::restoreInventoryFromArchive` | 从归档记录重建背包，数据形状与 markDirty 写入口径对称（`{inventory: {itemId: count}}`）；坏行/零计数防御性跳过。 |
| auth 接线 | 恢复优先级：**转移票据（P15）> 归档兜底（env 门控）> 装配预注入 > 全新背包**——票据缺席（TTL 过期/未导出）时读归档；装配层预注入的背包（inventories 构造参数）永不被恢复路径覆盖。 |
| env 门控 | `NYTHOS_ARCHIVE_RESTORE=1` 启用（缺省关闭）——存量验收依赖逐跑全新背包（如 verify-mmorpg step8 的 potion=4 精确断言会被跨跑恢复破坏），零破坏口径与 P13 治理开关同范式。 |

### 1.2 玩家初始血量外置（blueprint/24 §四 边界项）

- gameplay 表新增 `player` 段（`{maxHp: int≥1}`，optional 缺省 100）——schema/缺省表/参考表/反漂移测试四同步。
- `BasePlayer::initVitals(int $maxHp)`：auth 挂载时一次性覆盖基线并回满（装备/临时修正未挂载，合成上限即基线）；
  缺省不调用 = 100 逐字节等价。
- `MapServer` 构造参数 `playerMaxHp`（factory 从 GameplayConfig 透传）；auth 在快照 hp 导入**之前**注入
  （importHp 的 clamp 上界依赖合成上限）。
- 边界：player.maxHp 的热载变更为登录时点语义（已在场玩家不受影响），不进 applyGameplayConfig 的热载 diff。

### 1.3 verify 脚本公共库迁移（blueprint/26 §四 遗留项）

verify-combat / verify-phase5 / verify-room / verify-matching 四脚本迁移 P14 公共库（机械替换：
本地骨架 9 函数删除、bootVerifyGlobals 接管、步骤作用域定时器入登记表、看门狗保留普通 Timer::add）。
迁移暴露并修复的三处脚本与库的口径差异：

| 差异 | 处置 |
|---|---|
| verify-combat 的 `sendMap` 四参（显式 requestId） | 公共库 `sendMap` 增可选 `?string $requestId` 参数（缺省 reqId()），三参/四参调用点全兼容 |
| verify-room 的 `sendMap` 是批量发送器（`$GLOBALS['client']` 单连接模型，非 uid 注册表） | 原发送器改名 `sendRoomFrame` 本地保留（库迁移的「保留项」模式），20 个调用点机械改名 |
| 各脚本 `finishAll` 把 SKIP 误计入 FAIL | 公共库统一修正：summary/RESULT 增 `SKIP=%d` 列，SKIP 不再计入 FAIL（verify-room 的 RESULT 由恒 FAILED 修正为 PASSED） |
