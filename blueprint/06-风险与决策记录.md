> （ADR-001~026，每份一个文件）——本文件只保留索引与摘录，不做第二权威源。

## 1. 风险与应对

### 风险 1：Actor 模型设计过早锁死

应对：

- 先定义最小 Actor API（`ActorInterface::update()`）。
- 不提前实现复杂 supervision。
- 不提前实现复杂 mailbox。
- 通过 Demo 验证。

### 风险 2：Cell / AOI 设计过度耦合

应对：

- Cell 只负责空间归属（只存 `entities: EntityId[]`）。
- AOI 只负责兴趣范围（AOIProvider / AOIQuery / InterestArea）。
- Event 负责业务事件。
- Network 负责传输。

### 风险 3：集群过早开发

应对：

```text
单进程 → 多 Actor → 多地图 → 多进程 → 跨进程 → 跨服务器
```

第一版完全不考虑 Cluster，不做分布式。分布式会放大所有设计错误。

### 风险 4：性能指标拍脑袋

应对：

Benchmark 驱动，而不是宣传数字驱动。每次 Benchmark 记录完整环境参数，形成 Benchmark v0.1 / v0.2 / ... 版本序列。

## 3. 开放决策清单（原规划期遗留，现况标注）

以下为 v0.1 规划期保持开放的决策；多数已在此后的演进中获得裁决：

1. ~~MessagePack vs Protobuf（协议序列化格式）~~ → 已裁决：双轨制，Map 频道二进制 + Social JSON，
   引擎另备 Msgpack/Protobuf 序列化器（[ADR-022](adr/ADR-022-序列化双轨制.md)）。
2. ~~Redis 服务发现 vs 独立 Registry~~ → 已裁决：RedisServiceRegistry（engine Cluster 模块）。
3. 固定 Tick vs 自适应 Tick → 部分裁决：base tick 固定 50ms，区域按密度分频降载（动态周期），
   房间按负载动态周期（blueprint/22）。
4. 单 Region vs 多 Region → 保持开放（RegionScheduler 预算机制已就位，多 Region Rebalance 待需求）。
5. MySQL 双写方案 → 保持开放（当前单表 upsert，见 [docs/persistence-guide.md](../docs/persistence-guide.md) §3）。
6. ~~热更新实现方式~~ → 已裁决：不立项热更层，配置热载 + 滚动重启 + GM 三件套覆盖
   （[ADR-026](adr/ADR-026-热更层裁决.md)）。
7. Kubernetes 部署方式 → 保持开放（容器化已交付，编排后置，见 docs/deployment.md）。
8. ~~多进程时 uid 寻址 / 进程间路由 / 服务注册：自研 vs gateway-worker~~ → 已裁决：全面自研单栈，
   移除 gateway-worker（[ADR-021](adr/ADR-021-移除gateway-worker统一网关栈.md)）。

原则：

> 先抽象接口，再根据 Benchmark 和真实需求决定实现。
