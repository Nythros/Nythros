> 文档定位：开服前稳定性验证（第 2 周清单）的首轮演练记录——soak 长跑与故障矩阵两套自动化演练的
> 首次实跑结果、抓到的缺陷与修复。演练器为仓库常驻工具（`benchmarks/soak-map.php` /
> `benchmarks/fault-drill.php` / `benchmarks/lib/drill-harness.php`），可在目标环境重复执行。
> 验收环境：WSL2 / Ubuntu / PHP 8.3.33 / Workerman 5.2.2 / Redis（127.0.0.1:6379）/ MySQL（systemd 服务）。

## 3. 长跑演练结果（3 分钟冒烟口径）

- 7 波次 × 10 客户端：认证 **100%**，波次帧率 875~1653 fps（单客户端 87~165 f/s），
  attack→hit 链路 P99 ≈ 80ms 稳定；
- RSS 斜率 **0.00 KB/采样**（最小二乘，无泄漏迹象）；4 个 worker 进程 RSS 全程平稳；
- 小时级长跑（--minutes=240 --clients=30）为开服前的例行任务，本记录覆盖首轮冒烟口径。

## 4. 演练抓到的缺陷与修复（核心价值）

### 4.1 心跳定时器无异常边界（engine/demo 级 bug）

Redis 宕机期间第一次心跳抛异常会**打死常驻定时器**——注册表从此不再回填，Redis 恢复后该实例
永久 503。修复：心跳回调自带 try/catch 兜底（与 PerfSampler/ArchivePipeline 的「只记日志」同口径）。
推论已写入 best-practices：**任何常驻周期任务的回调都必须自带兜底**。

### 4.2 心跳 meta 不完整（自愈契约破洞）

Redis 数据丢失（无持久化重启）后服务 hash 清空，仅 `{playerCount}` 的心跳合并产出缺
`mapId/wsAddress/status` 的残缺 meta——`selectChannel` 过滤链永久拒绝该频道，**必须重启 worker
才能恢复**，违背 ADR-028 的「恢复后免重启自愈」契约。修复：心跳携带与 register 完全相同的
完整 meta（`registryMeta()` 单一来源），首个心跳（≤5s）即无损重建注册条目。

### 4.3 压测客户端引擎腐化（工程债）

stress-map v1 的 Workerman AsyncTcpConnection 客户端随 ADR-021 单栈化后时序腐化
（10 客户端 25s 仅 3 个建链，单连接 ~10s），且 Workerman 缺省 `/tmp/workerman.pid`
是全局单例锁——start-maps master 在跑时压测脚本被 "already running" 拒绝。修复：
stress-map v2 重写为原生 socket + stream_select（与演练器共享已验证帧协议实现）；
start-maps/stress-map 各配独立 pidFile（G-5 同口径）。

## 5. 演练器自身的教训（编排层）

- **注入有效性必须确认**：`redis-cli shutdown` 是异步的，立刻重启会抢绑失败且 daemon 静默退出，
  整个后续演练被拖垮——注入后必须等端口真正释放，重启带重试，注入失败显式 SKIP 而非空转 PASS；
- **就绪判定 = 登录探针**：端口监听早于 registry 注册，只等端口会撞出 503 竞态窗口；
- **挂接模式要防半死栈**：检测到既有实例转挂接前，基线登录必须通过（首版在此空转过一轮）。

## 6. 遗留项

- 网络分区（tc/netem / 多机）无法单机演练，待多机环境补；
- CPU 容量标定仍需目标硬件复测（performance.md §6.4 清单不变）；
- 小时级长跑在本机的例行执行（建议开服前累计 ≥24h）。

## 7. 容量实测（stress-map v2 首轮阶梯，2026-08-30）

环境：WSL2 / i3-10105（4C8T 3.7GHz）/ 3.8GB / PHP 8.3.33。口径：全部客户端打进**同一个 map worker**
（map-1#ch-1，单核容量单元），互相全视野可见（O(N²) 广播扇出的最坏情况），每客户端 1 move/s；
CPU 为 map worker 进程自身 jiffies 占用（单核 = 100%）。

| 客户端 | map worker 单核占用 | 总帧率 | p99 延迟 | 结论 |
|---|---|---|---|---|
| 30 | ~20% | 7,084 | 130ms | 空闲 |
| 60 | 44.4% | 46,012 | 151ms | 舒适 |
| 120 | 75.0% | 122,913 | **309ms** | 膝点：延迟开始翻倍 |
| 240 | — | 153,789 | **1,211ms** | 过膝：延迟崩坏 |

单 worker 容量经验值（本机口径）：**worst-case 全视野混战 ≈ 60-90 人/worker（p99 ≤150ms），
120 人可承载但延迟退化**。实际游戏（视野受限 + 分频道 + 分频降载）远好于 worst-case：
本机 4 个 map worker（8 逻辑核）外推总量 ≈ 400-800 并发；正式容量以目标硬件按 performance.md §6.4
复测为准。瓶颈排序：单 worker 单核（广播扇出）→ 单客户端下行带宽（240 人时 ≈230KB/s/客户端）；
内存无压力（RSS 全程平稳）。

编排层教训（复测必读）：扩大账号表后 gateway 启动需做 N×bcrypt 哈希（260 账号 ≈16s），
容量阶梯必须等**登录探针就绪**而不是端口就绪，否则首轮波次全数撞在启动窗口上（首版实抓）。

### 平衡拓扑对照（--map-ids=map-1,map-2 → 3 频道）

单 mapId 时 240 人只落 map-1 的 2 个频道：ch-1 单核 **105%（超卖）** / ch-2 78%，18083/18084 空转；
`--map-ids` 轮转后 3 worker 各 ≈44%（combined 133%），**单 worker 过热解除**；p99 347~582ms 与

### 优化信号（3h 最重要的发现）

`eventbus.dropped_total` 累计 **151 亿**（≈4.9 万次/秒，速率平稳）——droppable 低档帧的泄压

**事件入队/消费配比有数量级优化空间**（候选：视野分频下的同实体事件合并入队、信封批量粒度、
热 worker 的 eventbus 队列容量）。建议作为下一性能批次的立项输入。

## 9. 仪表修正与丢弃优化闭环（§8「优化信号」的诚实修订）

§8 记录的「151 亿丢弃（49k/s）」经源码核查为**两级虚高的仪表伪影**，本节为修正闭环：

### 缺陷 1（真 bug，已修复）：dropped_total 在 flush 时重加生命周期累计

`SimpleEventBus::flush()` 每次 flush（20 次/秒）把 `$droppedCount`（生命周期累计值）整个
`PerfProbe::increment` 进探针，经 PerfSampler 每 5s 单调累加进 Redis——导出速率 ≈ 累计值 × flush
次数，随运行时长虚增数个数量级。3h 的 151 亿反推真实累计仅 ≈39 万级。**修复**：丢弃计数改为在
`publishEnvelope()` 丢弃点即时上报（+1/次），flush 不再重加；探针窗口语义与 PerfProbe 对齐。
回归：SimpleEventBusTest 新增断言（丢 N 报 N，多次 flush 不膨胀），9/9 过。

### 修复后的真实数字（5 分钟 240 客户端复测）

守恒式交叉核对精确成立：`published(141,672) = dispatched(102,546) + dropped(39,126)`。
**39,126 次丢弃全部发生在每波 join 洪峰的瞬时**（≈4,900/波：百人同帧入场产生 O(J×N)≈28,800 个
enter 信封脉冲，超出 10k 队列上限），**稳态丢弃为 0**——此前「每秒 4.9 万常态泄压、入队/消费
配比数量级优化」的判断作废；真实结论是队列容量只需应对入场脉冲。

### 决策门判定与优化（批次 3）

- FrameMerger enter 去重：**跳过**（无稳态洪水可去重；join 洪峰是不同实体的 enter，去重无益）；
- 队列容量可配置：**采纳**——装配缺省 10k → 30k（`NYTHROS_EVENTBUS_QUEUE` 可覆盖），
  覆盖常规 join 洪峰；快照重同步（1s）仍是最终兜底；
- 复测验证：3 波 × 240 客户端 `dropped_total = 0`，`RESULT: PASS`。

### 复盘要点

1. 监控数字先问口径——「速率异常」的第一嫌疑人是仪表自身（本次虚高 386,000 倍）；
2. 守恒式（published = dispatched + dropped + in-flight）是免费的交叉校验器，perf-stats 已增显；
3. 「优化」的正确姿势是复测后的数据驱动裁剪：计划中的三项最终只做了一项半。

## 10. 长跑遗留问题修复轮（第二轮 soak 就绪性）

对 §7-§9 遗留问题逐项盘点后修复，共四项 + 一个连带抓到的环境兼容缺陷：

1. **frameMeanMs 采样断链（双重根因）**：a) 读错口径——`world.frame_ms` 由 `recordDuration` 写入
   totals/histogram 而非 counters，均值需 totals ÷ hist 桶计数和；b) **phpredis 6.x 的 `scan()`
   单次返回键数组**（游标耗尽后 false），逐键 while-assign 循环把数组喂给 `hGetAll` → TypeError
   被静默 catch——droppedTotal/frameMeanMs 自采样增强上线以来一直是 null（§8「151 亿」的虚高
   读数其实也受此影响：guard 侧读 null，从未真正触发）。两处 reader（drill-harness 与
   metrics-exporter）统一为 `scanKeys()` 兼容生成器；修复后实测 frameMean=6.1ms 出数、
   exporter 真实渲染 frame 直方图。**教训：catch 吞掉的 TypeError 让数据链路静默断了两轮演练
   ——观测代码的异常必须可见（exporter 的 scrape_errors 计数是正例）。**
2. **503 契约确定性**：`selectChannel` 的 discover 在 Redis 故障时可抛（RuntimeException/phpredis
   异常），裸传落 dispatch catch-all 的通用 500——与演练观察到的 `auth_failed 503 no available
   channel` 降级契约不一致（同一故障两种表现）。归一：注册表读失败 → null → 503 + 日志归因。
   故障矩阵 redis-down 场景复跑确认宕机窗口稳定 503。
3. **soak 不传 --map-ids**：均衡拓扑容量实测（§8）的能力没有接到长跑编排上——下次 240 客户端
   长跑仍会重演「两频道挤压」。补 `--map-ids` 透传（白名单过滤后拼 shell）。
4. 频道间漂移本体维持 ADR-029 提案态（触发条件未变，非本轮范围）。

### 核心问题裁决：§11 的「frameMean 逐波爬升」收敛了吗——收敛了，且冒烟观察是冷启动前 3 点

frameMean 是**生命周期累计均值**（totals ÷ hist 桶计数，跨 4 个 map worker 聚合）。2h 轨迹是
「冲高→回落→平台」而非持续爬升：w1=7.71 → **w8 峰值 9.35** → 单调回落 → w61 起进入 ~8.00 平台
（最后两个 20 波窗口 8.007 / 8.006，差 <0.001ms/波；后 10 波均值 8.034）。累计口径下平台即
瞬时稳态：**世界帧耗时稳态 ≈8.0ms，占 50ms tick 预算 16%**。

候选解释（走廊重叠度变化/怪物密度累积）被否定——两者只会单调恶化，观测到的恰是**衰减回归**：
更合理的机制是启动瞬态（join 洪峰的 enter 信封处理、AOI 索引与走廊初始分布收敛、
堆/arena 整形）抬高前 ~10 波，随后摊薄。冒烟的 4.86→5.77→6.23 是该瞬态窗口的前 3 个累计点，
不构成趋势证据。**判定：可放行 24h 累计长跑。**

### 13.2 关键反差：§11 观察点在基线收敛锁死，在 JIT 轮呈「后段真实缓降」（绝对水平仍全程占优）

frameMean 20 波窗口轨迹（生命周期累计口径）形态相反：

```
基线(no-JIT): w1-20=8.86 → w21-40=8.42 → w41-60=8.17 → w61-80=8.01 → w81-98=8.01 (冲高→回落→平台锁定)
JIT:          w1-20=7.02 → w21-40=7.34 → w41-60=7.25 → w61-80=7.38 → w81-98=7.56 (起步即最低→缓升)
```

- 基线：冷启动尖峰（w8=9.35）后单调回落，后半段斜率 **−0.0035ms/波**，末两窗口差 <0.001ms——
  §11 的爬升担忧证伪为冷启动瞬态（§12 已裁决）。
- JIT：无编译冷启动尖峰（tracing 惰性摊薄），但后半段**单调上升** +0.010ms/波（w50=7.26→w98=7.61，
  去首尾离群重算斜率不变，非噪声）。三向同证排除采样假象：后段 **fps 同步下降**
  （205,009→176,660，−772/波；基线同段 −247/波近于平）+ **p99 同步上升**（前10波 192→后10波 293ms）。
  加速比因此随时间侵蚀：中段峰值 fps +40%、p99 −61%，到 2h 末收窄为 fps +19%、p99 −19%——
  **但从未跌破基线**（末波 frameMean 7.61 仍低于基线平台 8.01）。

**候选解释（待验证假设，非本轮定论）**：符合 tracing JIT 长运行的已知退化模式——世界状态随波次
复杂化（§11 列过的走廊重叠/密度因素）使热 trace 逐步失效、侧退出增多，加速比回落但未穿底。
区分实验（24h 轮）：① 观察 frameMean 缓降斜率是否自身衰减（平台化）还是线性外推——线性外推
约在 3h 处回到基线水平，24h 尺度**必须确认收敛**，否则 JIT 净收益随时长归零甚至转负；
② 对照 `opcache.opt_debug_level` / `php -d opcache.jit_debug` 采样 trace 失效计数与波次相关性；
③ 可加一轮 `jit=1255`（静态 JIT）对照，若后段斜率归零则坐实 tracing 失效假说。
