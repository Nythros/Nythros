## 2. v0.1 冻结清单

v0.1 只冻结 7 个核心：

| # | 核心 | 职责 | 生命周期 | 依赖 | 不依赖 |
|---|---|---|---|---|---|
| 1 | Runtime Kernel | Clock、Event Loop、Scheduler 挂载点、Task Queue | 进程启动创建 → 常驻循环 → 进程退出销毁 | 无（仅 PHP 运行时） | World、Entity、业务 |
| 2 | World | 单地图服运行时聚合根，管理 EntityManager、ActorSystem、MapManager、EventBus、AOI、RegionScheduler | 进程启动组装 → 每帧按固定顺序 update → 进程退出销毁 | Kernel 的 Clock / Scheduler + 各组件接口 | 网络、协议、认证 |
| 3 | Entity | Identity、Position、Components/State、Lifetime | 创建 → 状态 / 位置变更 → 销毁 | 无 | Actor、网络、业务逻辑 |
| 4 | Actor | 行为与 Tick；可绑定一个 Entity 也可不绑定 | 创建 → 绑定 Entity（可选）→ 每帧 update → 销毁 | EntityInterface（可选绑定） | 具体 Entity 实现、网络 |
| 5 | Scheduler | TickScheduler、RegionScheduler、TimerWheel、TaskQueue；CPU Budget | 每帧运行 → 帧末清空任务 | Clock | 业务语义 |
| 6 | Cell / AOI | 空间索引；Cell 只存 `entities: EntityId[]`；AOI 暴露 AOIProvider / AOIQuery / InterestArea | 实体进入 / 移动 / 离开时更新 | Entity 的 Position | 业务状态、九宫格 API 承诺 |
| 7 | Event | EventBus：即时 / 延迟 / 区域事件 | 帧内产生 → flush 时派发 | Scheduler（延迟事件走 TaskQueue） | 客户端协议 |

### 冻结清单的依赖方向

```text
Runtime Kernel
     ↑
  Scheduler
     ↑
   World ── Entity / Actor / Cell-AOI / Event
```

World 只依赖接口（`Nythros\Contracts`），不依赖任何具体实现类。

## 3. 暂缓与后置清单

以下内容不进 v0.1，仅预留接口：

- **Protocol / Serializer 具体实现**：JSON / MessagePack / Protobuf 三选一后置。v0.1 只定义 Message → Serializer → Frame → Transport 的抽象管线。
- **Security 具体认证**：Engine 只保留 AuthenticatorInterface / SessionInterface / IdentityInterface。Token 实现（RedisTokenAuthenticator、JWTAuthenticator）属于 Gateway / Session 层，后置。
- **Cluster**：演进顺序为 单进程 → 多 Actor → 多地图 → 多进程 → 跨进程 → 跨服务器。第一版完全不考虑 Cluster，分布式会放大设计错误。
- **Persistence**：只定义存储接口，MySQL / Redis 落地后置。
- **Framework 业务模块**：Skill / Item / Buff / Quest / Inventory / AI 全部作为官方 Plugin 后置。第一版只有 BaseActor / BasePlayer / BaseMonster / BaseNPC。

## 4. 里程碑

| 里程碑 | 核心问题 | 验收驱动 |
|---|---|---|
| 原型能跑 | 这套核心架构能跑吗？ | 最小可运行骨架 5 帧稳定运行（`04-启动执行清单.md` 验收标准） |
| 引擎核心 | 核心能力是否稳定？ | 7 核心全部有测试、API 冻结、Benchmark 可重复 |
| 框架 | 开发者能否开始写游戏？ | 四基类 + 插件机制可用，业务代码不碰 Engine 内部 |
| Demo | 能否真正做出一个游戏？ | 多客户端跑通最小 MMO 游戏循环 |
| 发布 | 能否让别人使用？ | create-project 安装 → 启动 → 文档跟随完成 |
| 生态 | 能否形成生态？ | 官方插件、社区插件、文档网站、教程 |

所有里程碑按验收结果推进，不是按时间推进。

## 5. 每周固定节奏

### 周一

- 确认本周目标。
- 确认依赖。
- 明确验收标准。

### 周二～周四

- 开发。
- 测试。
- Benchmark。

### 周五

- 集成。
- 压测。
- 文档。

### 周末 / 阶段结束

回答三个问题：

1. 本周目标是否完成？
2. 是否发现架构问题？
3. 是否需要修改蓝图？

## 6. 开发铁律

1. **Engine 永远不知道 Framework。**
2. **先验证模型，再追求性能。**
3. **每一个核心模块必须有测试。**
4. **每一个性能结论必须有 Benchmark。**
5. **协议、安全、集群都必须可替换。**
6. **业务状态尽量封装在 Actor 内。**
7. **AOI 不与具体游戏业务耦合。**
8. **不要为了"未来可能需要"提前堆功能。**
9. **先做单机单进程正确性，再做集群。**
10. **先做一个真正能玩的 Demo，再扩展生态。**
