# Engine Architecture Specification v0.1

## 1. Overview

本文档是 PHP MMO 引擎的架构规范 v0.1，是全部代码工作的唯一架构依据。

项目定位：以 PHP 构建高性能 MMO 服务端体系。

```text
高性能引擎
     ↓
开箱即用框架
     ↓
开发者生态
```

架构驱动，不是功能驱动。Actor、Cell、Protocol、Security、Cluster 不是并列模块，而是生长在两个地基之上的能力：**Runtime Kernel** 与 **World**。

### v0.1 冻结的 7 个核心

v0.1 只冻结以下 7 个核心，它们的职责、生命周期、依赖关系、数据流、Tick 顺序、API 边界在本文档中定义清楚：

1. Runtime Kernel
2. World
3. Entity
4. Actor
5. Scheduler
6. Cell / AOI
7. Event

Protocol、Security、Cluster、Persistence 的具体实现，以及 Framework 的业务模块（Skill / Item / Buff / Quest / Inventory / AI），都不在 v0.1。

## 2. Architecture Layers

```text
Ecosystem（生态）

Framework（CLI / Base / Plugin）

Engine
 ├─ Runtime Kernel：Clock、Scheduler、Event Loop、Task Queue
 ├─ Infrastructure：Network、Protocol、Security Interface、Persistence、Cluster（后置）
 ├─ World：EntityManager、ActorSystem、MapManager、EventBus、AOI、RegionScheduler
 ├─ Entity（Player / Monster / NPC / ItemDrop / Projectile / Trigger）
 ├─ Actor（Player / Monster / NPC ...）
 └─ Spatial Index：Cell / AOI
```

### 分层原则

- 上层可见下层，下层永远不知道上层。Engine 永远不知道 Framework。
- World 是 Engine 内的运行时聚合根，组装并驱动 EntityManager、ActorSystem、MapManager、EventBus、AOI、RegionScheduler。
- Infrastructure 是能力接入层：Network、Protocol、Security、Persistence 都通过接口接入，实现可替换；Cluster 明确后置。
- Spatial Index 只做空间归属与查询，不持有任何业务状态。
- 允许的依赖方向：

```text
Framework → Engine
Demo      → Framework
```

- 禁止的依赖方向：

```text
Engine  → Framework
Engine  → Demo
Cell    → RPG
Actor   → Inventory
Network → Skill
```

## 3. Runtime Kernel

Runtime Kernel 是引擎的底层地基，负责进程内最基础的时间与调度能力：

- **Clock**：逻辑时钟，tick 记录 microtime 与 deltaTime。
- **Event Loop**：事件循环，v0.1 用纯 PHP `while` 循环验证，后续接入 Workerman。
- **Scheduler**：调度器的挂载点，每帧驱动 TaskQueue。
- **Task Queue**：帧内任务队列。

约束：

- Runtime Kernel 不依赖 World、不依赖 Entity、不依赖任何业务概念。
- Runtime Kernel 不绑定具体事件循环实现：`nythros/kernel` 提供抽象实现，`nythros/kernel-workerman` 提供基于 Workerman 的实现。
- Scheduler 承载 CPU Budget 的设计目标：每帧按 Region 分配时间预算（见第 7 章），Kernel 只提供时间与执行载体，不关心"谁在哪个 Region"。

## 4. World

World 是单地图服的运行时聚合根，运行于 Runtime Kernel 之上。

职责清单：

- 管理 EntityManager、ActorSystem、MapManager、EventBus、AOI、RegionScheduler。
- 每帧按固定顺序驱动以上组件（见第 9 章 Tick 顺序）。
- 提供 `WorldInterface` 作为唯一的对外访问入口。

明确不负责：

- 不直接处理网络连接与收发。
- 不处理协议编解码。
- 不做认证鉴权。

网络、协议、认证都属于 Infrastructure 或更上层的 Gateway / Session 能力。

## 5. Entity & Actor

### 两个概念

**Entity** 只有四样东西：Identity、Position、Components/State、Lifetime。它没有行为，没有 Tick。

**Actor** 拥有行为与 Tick。一个 Actor 可以绑定一个 Entity，也可以不绑定任何 Entity。

```text
玩家     = Entity + Actor
掉落物   = Entity（不是 Actor）
全局技能系统 = Actor（不绑定 Entity）
```

Entity 类型：Player / Monster / NPC / ItemDrop / Projectile / Trigger。Actor 类型：Player / Monster / NPC 等。

### 职责分离

| 概念 | 管什么 | 不管什么 |
|---|---|---|
| Entity | 身份、状态、位置、生命周期 | 行为、Tick、消息处理 |
| Actor | 行为执行、Tick、业务消息 | 空间归属、空间索引 |
| Cell | 空间位置（`entities: EntityId[]`） | 业务状态（不存 playerHp、playerPosition） |

## 6. Spatial Index & AOI

### Cell

Cell 只是空间索引单元，只存 `entities: EntityId[]`。Cell 不持有业务状态，不存 playerHp、playerPosition 之类的字段。

### AOI 抽象

Engine API 暴露三个 AOI 概念：

- **AOIProvider**：空间索引维护者，提供 `updateEntity(entity)` 与 `query(entity)`。
- **AOIQuery**：兴趣查询描述（以某实体或某位置为中心、某兴趣范围）。
- **InterestArea**：查询结果抽象（兴趣范围内的实体集合）。

API 不暴露 `getNineCells()`。

第一版用 Grid/Cell 实现（`nythros/aoi` 的 GridAOI），九宫格查询只是 Grid 实现的默认查询细节，不是 API 承诺。后续可以替换为 Quadtree / Radius / Sector 实现，业务层无感。

### 移动时 AOI 更新流程

1. 判断目标 Cell。
2. 从旧 Cell 移除。
3. 加入新 Cell。
4. 计算视野变化。
5. 广播进入 / 离开 / 状态更新事件。

## 7. Scheduler

Scheduler 是 Engine 的调度核心，四个组成部分：

- **TickScheduler**：每逻辑帧驱动。
- **RegionScheduler**：World 内的区域调度策略实现，受 Runtime 预算控制。
- **TimerWheel**：定时任务。
- **TaskQueue**：帧内任务队列。

### Region CPU Budget

每个逻辑帧，Scheduler 为每个 Region 分配固定时间预算：

```text
Region A Budget = 2ms
Region B Budget = 3ms
Region C Budget = 1ms
```

后续可扩展动态 Region Rebalance。预算由 Runtime 控制，RegionScheduler 在预算内执行本 Region 的 Actor 更新。

## 8. Event System

EventBus 提供三类事件：

- **即时事件**：publish 后本帧派发。
- **延迟事件**：走 Scheduler 的 TaskQueue，到期后派发。
- **区域事件**：与 AOI 结合，只派发给兴趣范围内的订阅者。

事件不直接用于客户端协议。客户端协议走 Network / Protocol 层。

事件必须明确以下字段：

- 来源（source）
- 类型（type）
- 时间戳（timestamp）
- 目标范围（scope）
- 是否可靠（reliable）
- 是否可丢弃（discardable）

## 9. Tick 顺序

每个逻辑帧固定执行，顺序不可变：

```text
1. Clock tick
2. Scheduler 分配 Region CPU Budget
3. ActorSystem 执行 Actor update
4. World 处理 Entity 状态 / 位置变更
5. AOI 更新空间索引
6. EventBus flush
7. Network outbound flush
```

## 10. API 边界

Engine 只暴露接口，具体实现标记 `@internal`。

v0.1 冻结的接口清单（定义在 `nythros/contracts`，命名空间 `Nythros\Contracts`）：

```php
interface ClockInterface
{
    public function tick(): void;
    public function now(): float;
}

interface SchedulerInterface
{
    public function addTask(callable $task, int $priority = 0): void;
    public function runFrame(): void;
}

interface WorldInterface
{
    public function getEntityManager(): EntityManagerInterface;
    public function getActorSystem(): ActorSystemInterface;
    public function getAOI(): AOIProviderInterface;
    public function getEventBus(): EventBusInterface;
}

interface EntityInterface
{
    public function getId(): string;
    public function getPosition(): array;
}

interface ActorInterface
{
    public function update(): void;
}

interface EntityManagerInterface
{
    public function add(EntityInterface $entity): void;
    public function remove(string $id): void;
    public function get(string $id): ?EntityInterface;
    public function all(): array;
}

interface ActorSystemInterface
{
    public function add(ActorInterface $actor): void;
    public function updateAll(): void;
}

interface AOIProviderInterface
{
    public function updateEntity(EntityInterface $entity): void;
    public function query(EntityInterface $entity): array;
}

interface EventBusInterface
{
    public function publish(string $event, array $payload = []): void;
    public function subscribe(string $event, callable $listener): void;
}
```

约定：

- 具体实现类（SystemClock、SimpleScheduler、SimpleEntityManager、SimpleActorSystem、SimpleEventBus、GridAOI、World）标记 `@internal`，不构成 API 承诺。
- Framework 不得直接依赖 Workerman、Protobuf / MessagePack、Redis、具体 AOI 算法。
- 跨层通信一律通过 `Nythros\Contracts` 中的接口。

## 11. Infrastructure 接口预留

### Network

传输层抽象：`Transport` 接口定义 send / receive 语义。具体实现（WebSocket / TCP / Internal RPC）后置，`nythros/network` 提供接口，`nythros/network-workerman` 提供实现。

### Protocol

传输无关的协议管线：

```text
Message → Serializer（JSON / MessagePack / Protobuf）→ Frame → Transport（WebSocket / TCP / Internal RPC）
```

禁止 Message 与 Workerman Protocol 或 Protobuf 绑死。Serializer 三选一后置，先抽象接口。

### Security

Engine 只提供接口：

- `AuthenticatorInterface`
- `SessionInterface`
- `IdentityInterface`

Token 认证是 Gateway / Session 层能力，不是 Engine Kernel 能力。具体实现（RedisTokenAuthenticator、JWTAuthenticator 等）可替换。

Token 要求（归属 Gateway / Session 层）：

- 短 TTL
- 一次性消费
- 与 uid / map / session 绑定
- 防重放
- 认证失败后立即断开连接

### Persistence

只定义存储接口，具体存储（MySQL / Redis）后置。

### Cluster

明确后置。演进顺序：

```text
单进程 → 多 Actor → 多地图 → 多进程 → 跨进程 → 跨服务器
```

第一版完全不考虑 Cluster。分布式会放大所有设计错误。

## 12. Framework

Framework 保持轻量，避免变成大型 RPG 框架。

第一版只提供 4 个基类：

- BaseActor
- BasePlayer
- BaseMonster
- BaseNPC

Skill / Item / Buff / Quest / Inventory / AI 全部作为官方 Plugin 后置，通过 Plugin 机制接入。

## 14. 下一步行动

1. 冻结 7 核心（本文档第 1 章）。
2. 实现 Runtime Kernel 最小版（SystemClock + SimpleScheduler）。
3. 实现 World / Entity / Actor（最小接口与实现）。
4. 实现 Cell/AOI + EventBus（GridAOI + SimpleEventBus）。
5. 跑通单进程 Demo（`04-启动执行清单.md`）。
6. 引入 Workerman，接入网络与协议。
7. 完善 AOI、落地 RegionScheduler 与 CPU 预算。

## 附录

### A. 项目愿景与最终目标

> 先做高性能 MMO 引擎 → 再做开箱即用框架 → 最终形成开发者生态。

```text
开发者
   │
   ▼
composer create-project ...
   │
   ▼
启动服务器
   │
   ▼
创建 Actor / Map / Skill
   │
   ▼
直接开发游戏业务
   │
   ▼
多人在线游戏
```

### B. 两条通信线路

```text
控制线：   Client → Gateway → 全局业务服务
实时数据线：Client → Token → Map Server
```

控制线承载：登录、鉴权、聊天、组队、匹配、全局通知。

实时数据线承载：移动、战斗、技能、AOI 广播、高频状态同步。

核心思想：高频实时逻辑不要全部压在 Gateway 上。

进程职责划分：Gateway 负责连接、登录与全局业务；Map Server 负责高频实时逻辑；Redis 负责临时状态、Token、服务发现；MySQL 负责持久化数据。

### C. 移动时 AOI 更新流程

1. 判断目标 Cell。
2. 从旧 Cell 移除。
3. 加入新 Cell。
4. 计算视野变化。
5. 广播进入 / 离开 / 状态更新事件。

### D. 事件字段要求

每个事件必须明确：

| 字段 | 说明 |
|---|---|
| 来源 | 谁产生的事件 |
| 类型 | 事件类型标识 |
| 时间戳 | 产生时间 |
| 目标范围 | 派发范围（全局 / 区域 / 单目标） |
| 是否可靠 | 是否需要可靠投递 |
| 是否可丢弃 | 过载时是否允许丢弃 |
