# ADR-022：序列化双轨制（MessagePack + Protobuf）

> 状态：已接受（2026-08-24，用户批准）。
> 关闭：blueprint/06 开放决策「MessagePack vs Protobuf」（答案：都做，双轨）。
> 关联：ADR-020（三层定位与产品基线）、engine protocol namespace 既有 Serializer 抽象。

## 1. 背景

protocol namespace 已有 `SerializerInterface` 抽象与两个实现：`JsonSerializer`（调试友好）、`BinaryBatchSerializer`（词表驱动的二进制批量格式）。开放决策曾纠结单一格式选型；产品重定位后客户端承诺仅为「服务端协议文档」（决策基线 4），序列化格式成为开发者的可选项而非引擎立场——选型问题转化为「把选择权交给开发者」。

## 2. 决策

1. **双实现**：MessagePack 与 Protobuf 都实现，由既有 `SerializerInterface` 抽象承载，开发者按需选择；引擎不预设偏好。
2. **依赖策略**：engine 对 `ext-msgpack` 与 protobuf runtime 走 composer `suggest`（软依赖）；两个实现类常驻 protocol namespace，实例化时才要求扩展/包存在。默认安装零新增硬依赖，与「默认纯 PHP」性能天花板一致。
3. **proto3 IDL 兼作协议文档源**：选择 Protobuf 时，`.proto`（proto3）即协议文档唯一事实源，导出即交付（直接满足决策基线 4）。IDL 由使用方（starter-kit / 游戏项目）维护；engine 只提供通用 `ProtobufSerializer`，不内置任何业务 proto。
4. **默认建议**：新项目默认 MessagePack（schema-less、免代码生成、体积紧凑）；需要强契约、多语言客户端或文档驱动工作流时选 Protobuf。JsonSerializer 保留用于开发调试与工具链。

## 3. 承载方式

- `MsgpackSerializer implements SerializerInterface`：payload 数组 ↔ msgpack 二进制；帧结构与 BinaryBatchSerializer 同构（Frame 边界不变），仅编码段替换。
- `ProtobufSerializer implements SerializerInterface`：message ↔ protobuf 二进制；类型安全由生成的 message 类承担，Serializer 只做字节搬运。
- 选择点在组装层：starter-kit 于 deploy.yaml 声明 serializer 项并在 launch.php 装配；engine/framework 不感知具体选择——延续「Message → Serializer → Frame → Transport」既有协议抽象管线。
- 性能归位：两者均属热路径序列化，保留扩展替换点（msgpack 本身即扩展；protobuf C 扩展可选），本期不写自定义扩展。

## 4. 落地与验收

- 落地载体：MsgpackSerializer 可随 R2 引擎补强顺手落地；ProtobufSerializer 与 IDL 工作流为 R5 工程纵深明确项。
- 验收：多实现对拍测试（同 payload 编解码往返一致）；benchmark 序列补 MessagePack / Protobuf 与 Json / BinaryBatch 的吞吐对比数据，纳入 benchmark 门禁基线。

## 5. 状态

已接受。
