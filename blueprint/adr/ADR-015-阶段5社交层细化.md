### 1.3 路由规则（Events::onMessage 伪代码）

```php
public static function onMessage(string $clientId, string $data): void
{
    try { $msg = self::serializer()->decode(new Frame($data)); }
    catch (DecodeException $e) { sendToClient($clientId, Message::create('error', ['code'=>400, ...])); return; }

    $uid = self::gateway()->getSession($clientId, 'uid');   // null = 未认证
    if ($uid === null) {
        // 未认证只接受 auth，其余 404 宽容不关闭（沿用原 Gateway 口径）
        if ($msg->type === 'auth') { self::social()->handleAuth($clientId, $msg); return; }
        sendToClient($clientId, Message::create('error', ['code'=>404, ...], $msg->requestId));
        return;
    }
    // 已认证路由（不匹配 404 宽容不关闭）
    switch ($msg->type) {
        case 'chat:send':      self::social()->handleChat($clientId, $uid, $msg); break;
        case 'team:invite': ... case 'team:disband': self::social()->handleTeam($clientId, $uid, $msg); break;
        case 'map:enter':      self::social()->handleMapEnter($clientId, $uid, $msg); break;
        case 'map:join':       self::social()->handleMapJoin($clientId, $uid, $msg); break;
        case 'guild:join': case 'guild:leave': self::social()->handleGuild($clientId, $uid, $msg); break;
        default: sendToClient($clientId, Message::create('error', ['code'=>404, ...], $msg->requestId));
    }
}
```

每个 handler 内部 try/catch Throwable → `error{500}`（不关闭，客户端可重试；与各服务「Redis 异常 throw 而非 exit」先例一致）。

### 1.4 auth 流程（SocialService::handleAuth）

输入 payload 与原 login 相同（透传 StaticAuthenticator）。

```php
// ① authenticate → uid；失败 auth_failed{401} + closeClient
// ② mapId 白名单校验；失败 auth_failed{400} + closeClient
// ③ 单点登录：Gateway::getClientIdByUid(uid) 存在旧连接（排除本连接）→ closeClient(旧)（双开策略：踢旧连新）
// ④ 恢复判定：LocationStore::isOffline(uid)（EXISTS nythros:gw:offline:{uid}）
//    恢复模式：location = LocationStore::get(uid)（null 视为新登录）
// ⑤ 选频道（§3 状态机）：
//    discover('map') → 过滤 meta.mapId === mapId && status !== 'stopping'
//    恢复模式：再过滤 meta.channelId === location.channelId → 命中用之；未命中（原频道已死/stopping）→ 最少在线
//    新登录：最少在线（min meta.playerCount，缺失视为满员）
//    空 → auth_failed{503 'no available channel'} + closeClient
// ⑥ 签发 token：tokenManager->issue(uid, mapId, ['map'], 30)（失败 → auth_failed{500} + closeClient）
//    顺序保证：先选频道后签发，频道失败不产生孤儿 token
// ⑦ Gateway::bindUid(clientId, uid)；setSession('uid', uid)；setSession('loc', [mapId, channelId])
// ⑧ 写位置快照：LocationStore::set(uid, mapId, channelId)（SETEX 300）
// ⑨ 恢复分组：
//    teamId = TeamStore::findByUid(uid) → 存在：joinGroup('team:{teamId}') + setSession('teamId')
//    guildId = GuildStore::findByUid(uid) → 存在：joinGroup('guild:{guildId}') + setSession('guildId')
//    joinGroup('map:{mapId}:{channelId}')（登录即进频道组——auth 已分配频道）
// ⑩ LocationStore::clearOffline(uid)（DEL 掉线标记）
// ⑪ auth_ok{uid, token, map:{wsAddress, mapId, channelId},
//            team: {teamId, leaderUid, members}|null, guild: {guildId, members}|null}
```

说明：
- 不再调用 `registry->bind('map', uid, serviceId)`：resolve 的消费方（Chat 认证/Team 队长寻址）已随 RPC 删除；位置快照 `nythros:gw:location:{uid}` 全面替代（bind/resolve 接口保留供副本分配复用，见 §7-7）。
- 队伍信息从 `nythros:gw:team:{teamId}` hash 读 members/leaderUid 随 auth_ok 下发（客户端重建队伍 UI）。

### 1.5 chat:send 五语义

```php
// payload: {scope, content, targetUid?, mapId?, channelId?}（scope/content 缺失或非字符串 → chat:error{400}）
switch ($scope) {
    case 'world':
        Gateway::sendToAll(enc(chat:message{scope:'world', content, fromUid}), null, $clientId);  // 排除发送者（MINOR-R8 沿用）
    case 'channel':
        $loc = session('loc');  // auth/map:join 维护
        if (payload 带 mapId/channelId 且 != $loc) → chat:error{404 'channel unknown'};  // 只允许本频道发言（防跨频道）
        Gateway::sendToGroup("map:{$loc['mapId']}:{$loc['channelId']}", enc(chat:message{scope:'channel',...}), $clientId);
    case 'team':
        $teamId = session('teamId')（session 缺失时回退 TeamStore::findByUid）
        无队 → chat:error{404 'not in team'};
        Gateway::sendToGroup("team:{$teamId}", enc(...), $clientId);
    case 'guild':
        同 team 逻辑，组 "guild:{guildId}"；无帮 → 404 'not in guild'
    case 'private':
        payload.targetUid 缺失/空/非字符串 → 400；
        !Gateway::isUidOnline(targetUid) → chat:error{404 'target offline'};
        Gateway::sendToUid(targetUid, enc(chat:message{scope:'private', ...}));
    default: chat:error{400 'unknown scope'};
}
// 无命中不报错（world 无人/sendToGroup 空组 = 正常完成）；region scope 已删除（依赖的 chat:region_players RPC 全删）
```

### 1.6 组队状态机（TeamStore：边界矩阵判定入 Lua，多 Business 进程并发安全）

原 TeamServer 内存态 + 「单进程串行」前提（MAJOR-7）在 BusinessWorker count>1 下失效，判定逻辑必须原子化。TeamStore 用 5 个 Lua 脚本做读改写，返回码枚举：

```
0=ok  1=not_leader  2=target_in_team  3=team_full  4=invite_not_found
5=invite_not_for_you  6=already_in_team  7=team_not_found  8=not_member
9=target_is_sender（自邀）
```

`target_offline` 不进 Lua（Gateway 在线态无法在 Redis 内判定）：PHP 侧 pre-check `isUidOnline`，竞态窗口（检查后掉线）由 sendToUid 自动丢弃兜底。

**三条跨进程不变量（BLOCKER-1/BLOCKER-2/MAJOR-2 修复，本节全部 Lua 伪代码统一遵守）**：

- **TTL 同步续期（BLOCKER-1）**：`team:{teamId}` 每次写操作 EXPIRE 续期，但成员键 `uid-team:{m}` 若只在 join 时 SETEX 会先于队伍过期——「已在任意队伍」判据（uid-team 键存在性）随之失效，玩家可入第二队。故**所有写队伍的 Lua 脚本在 EXPIRE team 时，必须遍历 members 给每个成员 `SETEX uid-team:{m}` 同 TTL**（建队分支仅 sender 一个成员，accept/leave/reject/disband 按当前 members 快照遍历）。
- **cjson 编码约定（MAJOR-2）**：hash 内 `members`/`invites` 是 JSON 字符串，脚本内先 `cjson.decode` 成数组再操作（append/删除/计数），写回前 `cjson.encode`；`leaderUid` 为纯字符串直接读。
- **键名动态构造约束（BLOCKER-2）**：senderTeamId 判定入 Lua 后，`team:{teamId}` 键名在脚本内用 `'team:'..teamId` 字符串拼接动态构造。demo 规模单机 Redis 无 cluster 分片，此写法成立；若未来迁 Redis Cluster，需对 team 相关键统一加 hash tag 保同 slot（阶段 5 不处理，文档化为约束）。

**invite Lua**（KEYS: uid-team:{sender}, uid-team:{target}, team:seq; ARGV: sender, target, now, maxSize, teamTtl）：
```lua
-- BLOCKER-2：senderTeamId 读判移入 Lua（不再 PHP 预取），建队与判队同脚本原子
if ARGV[1] == ARGV[2] then return {9} end                  -- MAJOR-2 自邀判定
if redis.call('EXISTS', KEYS[2]) == 1 then return {2} end  -- target_in_team（MAJOR-1 修复：提前到建队判定前，两分支共享；原建队分支漏判 → 无队 sender 邀请已入队 target 假成功。判定顺序随之从「not_leader 先于 target_in_team」调整为「target_in_team 先于 not_leader」）
local senderTeamId = redis.call('GET', KEYS[1])            -- uid-team:{sender}（false = 无队）
local teamId
if senderTeamId == false then
    teamId = 'team-' .. redis.call('INCR', KEYS[3])        -- Lua 内 INCR seq，与判队原子
    redis.call('HSET', 'team:'..teamId, 'leaderUid', ARGV[1],
        'members', cjson.encode({ARGV[1]}),
        'invites', cjson.encode({{targetUid=ARGV[2], expiresAt=ARGV[3]+30}}))
    redis.call('EXPIRE', 'team:'..teamId, ARGV[4])
    redis.call('SETEX', KEYS[1], ARGV[4], teamId)
    return {0, teamId, ARGV[1]}                            -- MAJOR-2 建队分支显式 return（invites 即写发给 target 的条目，与既有队分支 append 语义一致）
end
teamId = senderTeamId
local team = redis.call('HGETALL', 'team:'..teamId)
if next(team) == nil then return {7} end                   -- team hash 缺失（键存在但被清空，理论不出现）
if team['leaderUid'] ~= ARGV[1] then return {1} end        -- not_leader
local members = cjson.decode(team['members'])              -- MAJOR-2 cjson.decode
if #members >= tonumber(ARGV[3]) then return {3} end       -- team_full
local invites = cjson.decode(team['invites'])
-- invites 幂等：已存在同 target 条目 → 刷新 expiresAt=now+30，返回 ok（重复邀请幂等）
-- 否则 append {targetUid=target, expiresAt=now+30}
redis.call('HSET', 'team:'..teamId, 'invites', cjson.encode(invites))
redis.call('EXPIRE', 'team:'..teamId, ARGV[4])
for _, m in ipairs(members) do
    redis.call('SETEX', 'uid-team:'..m, ARGV[4], teamId)   -- BLOCKER-1 TTL 同步续期
end
return {0, teamId, team['leaderUid']}
```

**accept Lua**（MAJOR-7 顺序原样保留；「已在任意队伍」判据 = uid-team 键存在性——等价于原「findTeamByUid 命中」且天然跨进程原子。KEYS: uid-team:{uid}, team:{teamId}; ARGV: uid, teamId, now, maxSize, teamTtl）：
```lua
if redis.call('EXISTS', KEYS[1]) == 1 then return {6} end -- ③ already_in_team（先于队伍不存在判定）
local team = redis.call('HGETALL', KEYS[2])
if next(team) == nil then return {7} end                  -- ④ team_not_found
local members = cjson.decode(team['members'])             -- MAJOR-2 cjson.decode
local invites = cjson.decode(team['invites'])
-- invites 解析：无发给 uid 的条目 → 存在未过期条目（发给他人）? return 5 : return 4；条目过期 → return 4
if #members >= tonumber(ARGV[4]) then return {3} end      -- ⑤ team_full
members[#members + 1] = ARGV[1]                           -- append uid
-- 删该邀请条目（发给 uid 的那条）
redis.call('HSET', KEYS[2], 'members', cjson.encode(members), 'invites', cjson.encode(invites))
redis.call('EXPIRE', KEYS[2], ARGV[5])
for _, m in ipairs(members) do
    redis.call('SETEX', 'uid-team:'..m, ARGV[5], ARGV[2]) -- BLOCKER-1 TTL 同步续期
end
redis.call('SETEX', KEYS[1], ARGV[5], ARGV[2])            -- uid 本人键（已在 members 内，显式补写保一致）
return {0, members}
```

**MAJOR-7 防御性清除的降级**（与单进程版差异，文档化）：原实现 accept 成功后遍历全部队伍清该 uid 的残余邀请。Lua 版以 uid-team 键为「已在队」唯一判据——不变量「一 uid 一队」不破（第二次 accept 被 ③ 拦截）。残余邀请在离队后「复活」的窗口 = 邀请 30s 过期窗口内「离队 → 立即 accept 旧邀请」，且该 accept 合法（对方 30s 内邀请过自己），行为可解释、不破坏不变量。裁决：放弃全量扫描清除，改由离队时清本队 invites 中发给自己的条目（低成本部分防御）。

**reject Lua**（KEYS: team:{teamId}; ARGV: uid, teamId, now, teamTtl）：
```lua
local team = redis.call('HGETALL', KEYS[1])
if next(team) == nil then return {4} end                  -- 队伍不存在 → invite_not_found
local invites = cjson.decode(team['invites'])             -- MAJOR-2 cjson.decode
-- 无自己条目 → 有未过期邀请 ? 5 : 4；过期 → 4
-- 删自己条目
local members = cjson.decode(team['members'])
redis.call('HSET', KEYS[1], 'invites', cjson.encode(invites))
redis.call('EXPIRE', KEYS[1], ARGV[4])
for _, m in ipairs(members) do
    redis.call('SETEX', 'uid-team:'..m, ARGV[4], ARGV[2]) -- BLOCKER-1 TTL 同步续期
end
return {0, team['leaderUid']}
```

**leave Lua**（KEYS: uid-team:{uid}, team:{teamId}; ARGV: uid, teamId, teamTtl）：
```lua
local team = redis.call('HGETALL', KEYS[2])
if next(team) == nil then return {8} end                  -- 队伍不存在 → not_member
local members = cjson.decode(team['members'])             -- MAJOR-2 cjson.decode
-- 判定 uid ∈ members，否则 return {8}
if team['leaderUid'] == ARGV[1] then
    -- 队长离开 = 解散：DEL team（invites 一并清除）+ 遍历 members DEL uid-team
    redis.call('DEL', KEYS[2])
    for _, m in ipairs(members) do redis.call('DEL', 'uid-team:'..m) end
    return {0, 'disbanded', members}
else
    -- 成员离开：members 移除 uid + HSET/EXPIRE + DEL uid-team:{uid}
    local invites = cjson.decode(team['invites'])         -- MAJOR-2 cjson.decode
    -- 删本队 invites 中发给自己的条目（低成本部分防御，落实 §1.6 MAJOR-7 降级说明）
    --（移除后）遍历剩余 members SETEX uid-team 同 TTL（BLOCKER-1）
    redis.call('HSET', KEYS[2], 'members', cjson.encode(members), 'invites', cjson.encode(invites))
    redis.call('EXPIRE', KEYS[2], ARGV[3])
    redis.call('DEL', KEYS[1])
    for _, m in ipairs(members) do
        redis.call('SETEX', 'uid-team:'..m, ARGV[3], ARGV[2])  -- BLOCKER-1
    end
    return {0, 'left', members}
end
```

**disband Lua**（KEYS: team:{teamId}; ARGV: uid, teamId, teamTtl）：不存在 → 7；leaderUid ≠ uid → 1；解散同 leave 的 disbanded 分支（DEL team + 遍历 members DEL uid-team）。

**PHP 侧动作（SocialService::handleTeam，按返回码映射 team:error{code, message}）**：
```
code 1→403 not_leader; 2→409 target_in_team; 3→409 team_full; 4→404 invite_not_found;
5→403 invite not for you; 6→409 already_in_team; 7→404 team_not_found; 8→403 not_member;
9→400 target_is_sender（自邀）
```
成功路径通知（全部经 Gateway，离线自动跳过）：
- invite ok → joinGroup(本连接, 'team:{teamId}') + updateSession('teamId')（MAJOR-2 修复：建队分支 sender 原无队，须补分组/会话才能收到后续 joined/left/disbanded 通知且 session 不陈旧；已有队邀请场景重复 joinGroup/updateSession 幂等，与 accept 分支对齐）→ sendToUid(target, team:notify{type:'invited', teamId, uid:target, fromUid:sender}) + team:ok{teamId, action:'invite'}（成功回执 MAJOR-5 沿用）
- accept ok → joinGroup(本连接, 'team:{teamId}') + updateSession('teamId') → sendToGroup(team:{teamId}, team:notify{type:'joined', teamId, uid}) + team:ok
- reject ok → sendToUid(leaderUid, team:notify{type:'rejected', teamId, uid}) + team:ok
- leave ok(成员) → sendToGroup(team:{teamId}, team:notify{type:'left', ...})（离开者还在组内，能收到）→ leaveGroup(本连接) + updateSession('teamId', null) + team:ok
- leave/disband ok(解散) → sendToGroup(team:{teamId}, team:notify{type:'disbanded', ...}) → 遍历 members：getClientIdByUid → leaveGroup(各在线连接, 'team:{teamId}') + 清各在线成员 session('teamId') + team:ok

邀请过期清理：无 60s Timer 全量扫描（Redis 全量扫描不现实）；纯惰性判定（accept/reject 判 expiresAt，过期返回 4）。invites 列表增长边界：仅 accept/reject/leave/disband 删除对应条目，过期邀请残留于 hash 直至队伍 TTL 600s 过期清空——demo 规模（maxSize 限队规模 + 邀请 30s 过期窗口）下可控，文档化为已知边界。

### 1.7 map:enter（进图凭证）与 map:join（进图/切图上报）

**BLOCKER-3 修复：token 单次消费（per-scope 墓碑）下，切图/重连无新凭证 → 新增 `map:enter`/`map:entered` 凭证续签契约。**

map:enter（上行，客户端需要连/换 Map 时发起）：
```php
// payload {mapId}：客户端切图、Map 断线重连、滚动更新强制 stop 后重连，均先发 map:enter 申请新凭证
// ① mapId 白名单校验 → 400
// ② 选频道（复用 §1.4 ⑤ 分配过滤：discover('map') → mapId === → status !== stopping → 最少在线）→ 空 503 'no available channel'
// ③ tokenManager->issue(uid, mapId, ['map'], 30)（先选频道后签发，频道失败不产生孤儿 token；失败 → map:error{500}）
// ④ 下发 map:entered{token, map:{wsAddress, mapId, channelId}}
// ⑤ 不写位置快照、不 joinGroup（等客户端连上 Map 后走 map:join 上报确认）
```
map:entered（下行）= 一次性凭证：客户端用它连 Map，Map consume('map') 成功后该 token 作废；下次再切图/重连必须重新发 map:enter 拿新 token。auth_ok 里的 token 仍作为「登录即进图」的首个凭证（§1.4 ⑥），二者共用同一 `issue(uid, mapId, ['map'], 30)` 语义——区别仅 auth 顺带完成登录分组，map:enter 只续签凭证。

map:join（上行，客户端连上 Map 后上报）：
```php
// payload {mapId, channelId, x?, y?}：客户端连上 Map 后上报（Map 认证成功即可发）
// ① mapId 白名单校验 + channelId 非空字符串白名单（进入 groupId/键构造，收敛注入面）→ 400
// ② 读旧 loc = session('loc')；新旧不同 → leaveGroup(clientId, 'map:{旧mapId}:{旧channelId}')
// ③ LocationStore::set(uid, mapId, channelId, x, y)（SETEX 300，覆盖写）+ updateSession('loc')
// ④ joinGroup(clientId, 'map:{mapId}:{channelId}')
// ⑤ map:joined{mapId, channelId}（确认回执）
```
auth 时已按分配频道 joinGroup，map:join 是「实际进图确认 + 切图」。信任客户端上报（demo 规模文档化：撒谎顶多恢复到自己报的位置）。map:enter 与 map:join 分工：map:enter 拿凭证、map:join 报位置，两者可连续发（切图 = map:enter 选新频道 → map:entered 拿 token → 连新 Map → map:join 更新位置）。

### 1.8 onClose / 重连

```php
public static function onClose(string $clientId): void
{
    $uid = Gateway::getSession($clientId, 'uid');
    if ($uid !== null) {
        LocationStore::markOffline($uid);   // SETEX nythros:gw:offline:{uid} 300 '1'
        // 位置快照/队伍/帮派均保留（恢复用）；解绑/退组 gateway-worker 内置自动完成
    }
}
```
- 掉线标记 TTL 300s < 队伍 TTL 600s：玩家 5 分钟内重连 → 恢复分组；5~10 分钟重连 → 队伍还在（TeamStore::findByUid 命中）照常恢复；>10 分钟 → 队伍键与 uid-team 键自然过期，按新登录。三层一致性由 TTL 阶梯保证。
- 恢复模式不重新走 mapId 白名单之外逻辑，auth 统一处理（§1.4）。
- 备选兜底：若目标 gateway-worker 版本 onClose 不可读 $_SESSION（个别版本差异），退化为 Events 静态内存 clientId→uid 映射（reload 丢失 = 掉线标记缺失 = 恢复降级为新登录，可接受）；实施时验证后定。

### 1.9 guild 最小实现

- `guild:join{guildId}`：GuildStore::join(uid, guildId)（hash members append + SET uid-guild:{uid} 无 TTL）→ joinGroup + updateSession → guild:joined。
- `guild:leave{guildId}`：非成员 403 → 移除（最后一人离帮删 hash）→ leaveGroup → guild:left。
- 帮派持久状态（无 TTL）：成员关系写入者只有 guild:join/leave；聊天消费 joinGroup 分组。

## 2. Redis 键设计（nythros:gw: 前缀，与 token:/svc: 严格三前缀隔离）

| 键 | 类型 | 内容 | TTL | 写时机 | 读时机 |
|---|---|---|---|---|---|
| `nythros:gw:offline:{uid}` | SETEX | '1' | 300s | onClose | auth 恢复判定 |
| `nythros:gw:location:{uid}` | SETEX JSON | {mapId, channelId, x, y, updatedAt} | 300s | auth 成功 / map:join / 切图 | auth 恢复（选原频道） |
| `nythros:gw:team:{teamId}` | hash | {leaderUid, members:JSON list, invites:JSON list} | 600s（每次写操作 EXPIRE 续期） | 5 个组队 Lua | auth 恢复（队伍信息下发）、队长判定 |
| `nythros:gw:team:seq` | INCR | 整数序列 | 无 | invite 建队 | — |
| `nythros:gw:uid-team:{uid}` | SETEX | teamId | 600s（随每次队伍写操作同步续期，见 §1.6 TTL 同步续期不变量） | Lua 内建队/accept/leave/disband + 写队伍时遍历 members 续期 | auth 恢复、「已在任意队伍」判据、team 聊天定位 |
| `nythros:gw:guild:{guildId}` | hash | {name, members:JSON list} | 无 TTL（持久） | guild:join/leave | auth 恢复、guild 聊天 |
| `nythros:gw:uid-guild:{uid}` | SET | guildId | 无 TTL（持久） | guild:join/leave | auth 恢复、guild 聊天定位 |

- **隔离**：`nythros:gw:`（社交临时/关系）∥ `nythros:token:`（凭证五态）∥ `nythros:svc:`（服务注册/发现）。gateway-worker 自身（Register/Gateway 内部寻址）不落 Redis。
- **注入面收敛**：uid/mapId/channelId/guildId 进入键名构造 → 白名单校验（uid: `[A-Za-z0-9_-]{1,64}`；mapId/channelId/guildId 沿用 SERVICE_ID 风格 `[A-Za-z0-9][A-Za-z0-9._#:-]{0,63}`），非法在 auth/消息入口拒绝（uid 这里是键后缀，比 RedisServiceRegistry 的「仅拒空」更严）。
- **teamId 格式**：`team-{seq}`（seq 来自 INCR）。
- **与 svc: 的关系**：`nythros:svc:uid:map:{serviceId}` 不再有写入方（bind 弃用），位置快照全面替代；`nythros:svc:map` 服务 hash + `hb:` 心跳仍由 Map 注册/续期、Business 消费（§3）。
- **x/y**：JSON 内允许 null（PHP json_encode 直写；无 Redis Lua cjson 限制）。

## 3. Map 滚动更新状态机（ADR-014 §5 细化）

### 3.1 状态字段与分配过滤

- Map register meta 增加 `status: 'serving'|'stopping'`（新 Map 启动即显式写 serving）。
- Business 分配过滤链：`discover('map')`（心跳键存活已内置）→ `meta.mapId === mapId` → `meta.status !== 'stopping'`（缺省视为 serving，向后兼容）→ 最少 playerCount。
- 标记 stopping 用 heartbeat 的 merge 语义（**零改动现有注册表**）：`$registry->heartbeat('map', $serviceId, ['status' => 'stopping'])` —— merge 只覆盖 status 字段，mapId/channelId/wsAddress 保留（register 的整体覆盖语义不可用：会丢字段）。

### 3.2 滚动更新流程（新 channelId 方案）

**裁决：滚动更新 = 新实例以新 channelId 注册**（如 `map-1#ch-1` → `map-1#ch-1b`，serviceId = `map-1#ch-1b`）。理由：同 serviceId 新旧并存时 HSET 覆盖 + 心跳互踩，discover 只见一份 meta，分配与 uid hash 全乱。换 channelId 复用既有 serviceId 编码与 channelId 解析（`strrpos('#')`），零格式改动。

```
1. 新 Map 启动：run-worker --service=map --mapId=map-1 --channelId=ch-1b --port=18084
   → register meta {mapId, channelId:'ch-1b', status:'serving', playerCount:0, wsAddress}
2. 标记旧实例 stopping（运维脚本）：
   php packages/demo/bin/map-rolling.php mark-stopping map-1#ch-1
   → heartbeat('map','map-1#ch-1',['status'=>'stopping'])
3. Business 立即不再把新玩家分到 map-1#ch-1（分配过滤 §3.1）
4. 旧实例玩家自然退出 / 掉线重连：恢复模式发现位置快照 channelId='ch-1' 的实例非 serving → 最少在线落到 ch-1b → 更新快照（重连自迁移，Business 无主动踢逻辑）
5. 运维观察：php packages/demo/bin/map-rolling.php watch map-1#ch-1 [--timeout=600]
   → 轮询 discover playerCount，归零 → 提示 stop 旧实例；超时未归零 → 提示强制 stop
6. 旧实例停止：SIGTERM 优雅 stop → onWorkerStop unregister（心跳键删除，discover 立即可见性下降）
```

**迁移策略裁决：自然退出 + 超时迁移结合**——平时靠自然退出与掉线重连迁移；超时（默认 600s）后运维强制 stop，未退出玩家断线 → 客户端重连后发 `map:enter` 申请新凭证（**客户端契约**：Map 断线/切图/滚动更新重连，一律先 `map:enter` 拿新 token 再连 Map，不依赖旧 token）→ Business 选频道落到 ch-1b → `map:entered` 下发新凭证。Business 侧零主动踢人逻辑（阶段 5 复杂度控制，见 §7-6）。

### 3.3 副本实例节奏区分

- 副本（dungeon serviceType，阶段 5 仅预留协议位）：生命周期 = 打完销毁（unregister 即终点），不滚动更新。
- 频道滚动更新 = 版本替换（新旧并存过渡 + stopping 窗口）；副本 = 生命周期终结（serving→销毁直落）。
- 副本分配（`dungeon:enter`，后续阶段）复用同一过滤：`discover('dungeon')` + status=serving + 最少在线——机制与频道分配完全一致，仅 discover 类型不同。

### 6.3 数据流方向对称性（检查清单第 1 项）

「一 uid 一队」跨多进程成立的双向核对：

1. **入队拦截双向**：invite 侧 `EXISTS uid-team:{target}` → 2（target_in_team）；accept 侧 `EXISTS uid-team:{uid}` → 6（already_in_team）。两方向独立拦截，任一 Business 进程并发触发必有一方命中，无双队窗口。✓
