# ADR-029：频道间负载再均衡（rebalance）

> 状态：**提议**（数据已立据，实现未排期）

## 背景

容量实测（blueprint/33 §7/§8）发现频道间负载失衡的两个层次：

1. **地图级失衡（结构性，已由部署解决）**：全部客户端请求同一 mapId 时，只会落入该地图的
   频道（map-1 → ch-1/ch-2），map-2/dungeon worker 空转。压测 `--map-ids` 轮转后消除——
   这是部署/客户端侧的拓扑问题，`selectChannel` 无责。
2. **频道级漂移（运行时，本 ADR 主题）**：同地图的频道间按 `playerCount` 登录时均衡，但玩家
   在频道间**不会迁移**——运行期负载会漂移（走廊聚集、玩法聚集、重建连接的先后差），
   实测出现 ch-1 105% / ch-2 78% 的单核过热，而相邻频道有余量。

## 决策（提议）

**立项「登录时已均衡 + 运行期再均衡」的第二期**：利用 P15 跨 map 迁移的既有机制
（转移票据 + detach 导出 / attach 重建 + 客户端驱动换线协议）实现**同图跨频道的
server 驱动再均衡**：

- 触发：心跳 meta 上报的负载指标（playerCount + 帧耗时 P99 + eventbus 丢弃率）超过
  频道间阈值差（如 max/min > 1.5 且热频道 core 估算 > 70%）持续 60s；
- 动作：热频道 select 一批 uid（按走廊聚类迁移，减少视野重算），经既有换线协议
  推送 `map:enter`（同图异频道，转移票据同图语义已有）；
- 反抖动：迁移后 120s 冷却，单波迁移 ≤ 频道人数的 20%。

## 理由

- 3h soak 证明**稳定性无虞**（RSS 零泄漏、auth 100%、p99 稳态 169ms），失衡是性能问题
  而非正确性问题——故只提案不紧急实现；
- 迁移机制的全部原语已存在（P15），实现成本低；新增的只有「触发器 + 选择策略 + 反抖动」；
- 不做运行时迁移的替代方案（多开频道 + 登录均衡）已够用至单地图 ~2 频道 × 90 人的规模，
  立项触发条件：单地图目标人数 > 150 或出现真实的频道过热事故。

## 影响 / 后果

- 迁移瞬间客户端有 1 次换线体验（既有协议语义，SDK 已内置重连即迁移）；
- 触发器依赖的心跳 meta 已含 playerCount（ADR-028 修复后完整），帧耗时/丢弃率需要补进 meta；
- 不得在战斗帧关键期（如 waves 进行中）迁移——选择策略需观察实体状态。
