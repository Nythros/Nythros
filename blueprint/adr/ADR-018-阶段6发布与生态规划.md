# ADR-018：阶段 6 发布与生态规划

> 状态：提议（阶段 6 规划，含 3 项建议决策与待确认点，最终以用户拍板为准）。
> 关联：blueprint `07-阶段实现清单.md`（阶段 6 任务与门禁）、`03-实施路线图.md`（发布里程碑与版本策略）、ADR-016（framework 与 Demo 方向，阶段 5 基线）、ADR-017（framework 层设计）。

## 1. 目标与门禁

- 目标：文档、打包发布、生态起步。
- 门禁：
  1. 新用户 `composer create-project` 后 10~30 分钟启动 Demo。
  2. Quick Start 可逐步执行，无卡点。

## 2. 发布前基线（现状盘点）

- 引擎核心：17 包 monorepo（13 基础核心包 + 2 后补包 + framework + demo），全部完成并验收。
  - 13 基础核心包：contracts、kernel、scheduler、entity、actor、event、aoi、world（阶段 1）+ kernel-workerman、network、network-workerman、protocol、security（阶段 2 网络/认证）。
  - 2 后补包：persistence、cluster（阶段 4）。
- Demo 完整可玩：`verify-combat PASS=9`（10 客户端跑通最小 MMO 游戏循环），`bin/server` 一条命令启动 + `make:actor` 一条命令创建 Actor 已就绪。
- 文档：blueprint 01-14 共 14 篇设计/验收/复盘文档已齐；但面向外部用户的使用文档（Quick Start 等）为零。
- 发布：未上 Packagist、无版本 tag、无 create-project 模板。

## 3. 三个关键决策

### 决策 1：包发布粒度（建议方案 A）

- 方案 A（推荐）：Engine 侧 15 个核心包合并为单包 `nythros/engine`；framework 独立为 `nythros/framework`；demo 独立仓库作 create-project 模板。符合蓝图「engine 与 framework 各自独立包」。
- 方案 B：17 包各自发布（维护繁琐，包间版本对齐与兼容矩阵成本高）。
- 方案 C：整仓发布（违反 Engine/Framework 分离铁律，铁律 1）。

理由：外部用户安装心智是「装一个 engine + 一个 framework」；15 个内部包的边界是工程实现细节，不应暴露给最终用户；Packagist 上多包版本同步与兼容矩阵难以长期维护。

### 决策 2：create-project 模板形态

模板仓库（独立 demo 仓库）含：

- `composer.json`：依赖 `nythros/engine` + `nythros/framework`；
- `config/`：deploy.yaml + 地图/技能/掉落配置；
- `bin/`：服务管理命令；
- 最小游戏示例：`make:actor` 骨架 + 几个 Monster。

理由：模板即「可运行的最小 MMO 起点」，用户安装后即有可玩的 Demo 骨架，`bin/server start` 一条命令起全链路，配合 Quick Start 满足 10-30 分钟启动门禁。

### 决策 3：文档分级

- 门禁必需：Quick Start（决定 create-project 门禁能否通过）。
- 高优先：Architecture、Actor Guide、Cell/AOI Guide。
- 渐进：Protocol / Security / Cluster / Framework Guide、FAQ、Troubleshooting。

理由：文档按「用户上手路径」分级——先保证 10-30 分钟启动门禁，再补架构与核心概念，最后补高级主题；避免文档齐头并进而延误发布节奏。

## 4. 实施顺序（7 步，依赖在前）

1. 发布基线：版本 tag `v0.1.0-alpha` + 包拆分（engine 合并 + framework 独立）。
2. create-project 模板（独立 demo 仓库）。
3. Quick Start 文档。
4. 门禁验证：create-project → 10-30 分钟启动。
5. 核心文档（Architecture / Actor Guide / Cell-AOI Guide）。
6. CI/Release（GitHub Actions + Packagist）。
7. 生态（长期，无门禁）。

## 5. 待确认点（需用户拍板，规划阶段不阻塞）

1. 包发布粒度：方案 A（engine 合并）是否采纳，还是 B / C。
2. 推进节奏：先做「① 版本 tag + 包拆分」工程基础，还是先做「③ Quick Start 文档」快速见效。

## 6. 遗留风险

1. 包拆分工程成本：15 包 → 1 包需 monorepo split 工具或手动合并，涉及 namespace、composer.json、autoload 整合与回归测试。
2. WSL2 保留端口：create-project 模板默认端口需避开 WSL2 保留端口，或文档化换端口方案。
3. 版本策略：engine `v0.1.0-alpha` → `v0.5.0-beta` → `v1.0.0`；当前 API 已冻结，从 alpha 起步（framework 同步）。
