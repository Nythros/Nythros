## 0. 最终决策总览

### 决策 A~G（用户已敲定，不可推翻）

- **A. 服务拓扑（三层）**：① 接入/社交层（低频，合并部署）：Gateway（登录认证）+ Chat（聊天）+ Team（组队），**接口分离（各自独立模块/消息协议）、部署默认合并到一个 social 进程、可配置拆开**；② 地图层（高频有状态）：多频道，每频道独立进程 + 独立 World，一进程一实例（性能隔离）；③ 存储/共享层：Redis（token / 服务发现 / 临时状态）。
- **B. 对称直连**：Chat/Team 收发都走自己的连接（不依赖 Map 下行），彻底贯彻「低频不掺地图」。Chat 维护玩家连接表（uid → 连接）；全服广播遍历连接表；私聊查 uid→连接，查不到（不在线）→ 404；区域/频道过滤需要 uid→(map,channel) 信息（通过 ServiceRegistry 的 uid 寻址获取）。客户端连接拓扑：登录（Gateway，短连）→ 拿 token + 各服务地址 → 分别连 Map 频道（长连，实时）+ Chat（长连）+ Team（长连）。
- **C. 配置驱动部署**：deploy.yaml 声明服务拓扑（服务类型、实例数、进程归属、端口）。低频服务默认合并 social 进程，未来压力大可改配置拆开（代码不动）。
- **D. 分机演进路径**（架构预留而非阶段 4 实现）：阶段 4 单机多进程（同机验证服务间通信 + 注册自愈）；阶段 5 社交 1 机 + 地图 N 机（改配置即可，ServiceRegistry 用 Redis、RpcClient 用 TCP 天然跨机）；阶段 6 地图分片（单图 5000 人需按区域分进程/分机，AOI 优化 + 位置同步降频）。分机是部署配置变化，架构已天然支持。
- **E. 多频道**：serviceId = `{mapId}#{channelId}`，meta={mapId, channelId, playerCount, wsAddress}，discover('map') 按 meta.mapId 过滤。
- **F. token 多授权**：单 token 绑定 uid + scopes（map/chat/team），per-scope 墓碑防重放，五态 Valid/Expired/Replayed/Invalid/Unauthorized。
- **G. 频道分配**：最少在线均衡 + 队长频道优先例外。

## 1. 服务拓扑（三层）【决策 A】

```text
┌─────────────────────────────────────────────────────────────────┐
│ ① 接入/社交层（低频：登录认证 + 聊天 + 组队）                        │
│    Gateway（登录/分配/签发） + Chat（玩家连接表） + Team（队伍状态）   │
│    接口分离：三个独立模块 / 独立消息协议 / 独立 serviceType           │
│    部署默认合并：一个 social 部署单元；可配置拆开（决策 C）            │
├─────────────────────────────────────────────────────────────────┤
│ ② 地图层（高频有状态：移动 + AOI，50ms 帧预算）                      │
│    map-1#ch-1 │ map-1#ch-2 │ map-2#ch-1 …                          │
│    每频道独立进程 + 独立 World；一进程一实例（性能隔离）；             │
│    频道间零内存共享，唯一交互面 = Redis + 跨服 TCP                   │
├─────────────────────────────────────────────────────────────────┤
│ ③ 存储/共享层：Redis（token 多 scope / 服务注册 / uid 寻址 / 临时状态）│
└─────────────────────────────────────────────────────────────────┘
```

### 1.1 三层职责与状态归属

| 层 | 服务 | serviceType | 状态 | 说明 |
|---|---|---|---|---|
| 接入/社交 | Gateway | `gateway` | 无状态 | token 在 Redis，天然水平扩展（count=N） |
| 接入/社交 | Chat | `chat` | 玩家连接表（uid→连接，轻状态） | 无状态业务逻辑 + 连接表，可水平扩展 |
| 接入/社交 | Team | `team` | 队伍状态（内存态） | 阶段 4 不持久化（重启丢失，文档化） |
| 地图 | Map | `map` | World 全量（EntityManager/ActorSystem/AOI/EventBus/Scheduler）+ 连接表 | 每频道一进程一 World |
| 共享 | Redis | — | token / 注册表 / uid 寻址 / playerCount | 唯一跨进程共享面 |
| 共享 | MySQL | — | 玩家状态归档（persistence，本阶段可裁剪） | 异步归档，见 10.5 |

### 1.2 「合并到 social 进程」的工程口径（已裁决：部署单元口径，MINOR-R6）

- **已裁决：部署单元口径**。Workerman 进程模型下，一个启动脚本 = 一个部署单元（master fork 出一组 worker 进程）。「social 合并」实现为 **social 部署单元**：同一启动脚本、同机同栈、共享启动/退出生命周期，内含 gateway / chat / team 三个 Worker 实例（各自端口、各 count=1）。
- **口径说明（显式写明）**：这是 Workerman 模型下对「低频三服务合并为一个服务进程」意图的**工程化实现**——共享启停生命周期 + 进程内可做共享优化（连接工厂等）；「合并」不指严格单 OS 进程单端口。
- 拆分 = deploy.yaml 把 chat/team 的 process 归属改为独立声明 → 独立脚本/独立进程组，**代码零改动**。
- 严格单 OS 进程单端口需「单端口多协议分发」（同一端口按帧头路由到三服务）——复杂度另计，**已裁决不取**，仅作实现变体记录；本 ADR 不再保留「需用户确认」待办。

## 2. 对称直连模型【决策 B】（推翻 v1「下行经 Map」）

### 2.1 客户端连接拓扑

```text
Client
  │ ① login（Gateway，短连）—— 登录成功即断开
  │    → login_ok{token, map:{wsAddress}, chat:{wsAddress}|null, team:{wsAddress}|null}
  │
  ├── ② Map 频道长连（实时：auth/move/AOI 视野事件）        scope 'map'
  ├── ③ Chat 长连（聊天收发全走这条连接，下行不依赖 Map）    scope 'chat'
  └── ④ Team 长连（组队收发全走这条连接，下行不依赖 Map）    scope 'team'
```

### 2.2 原则与推论

1. **低频不掺地图**：Chat/Team 的每一条上行与下行帧都走自己的连接。Map 进程不转发任何客户端聊天/组队下行帧（删除 v1 的 `chat:deliver` / `team:notify` 下行处理器）。
2. **Chat 维护玩家连接表**（uid → {conn, mapId, channelId, mapServiceId}）：全服广播遍历连接表；私聊查 uid→连接，查不到 → 404。
3. **Map 实例对 Chat 只提供查询型 RPC**（chat:region_players，见 6.3）：返回 uid 列表，投递动作由 Chat 在自己的连接表上完成——下行依旧全走 Chat 连接。
4. **「玩家在线」的口径按服务分别定义**：Chat 在线 = Chat 连接表命中；Team 在线 = Team 连接表命中；Map 在线 = uid 寻址（ServiceRegistry）命中。互不传递、互不阻塞。
5. **uid→(map,channel) 信息来源**：Chat 连接认证时从 ServiceRegistry resolve('map', uid) 获取 serviceId（编码含 mapId#channelId），解析后存入本地连接表（阶段 4 无换线，无陈旧问题）。

### 2.3 对 v1 的删除清单

- 删除：v1 第 10.2 章「下行链路（Chat → Map 实例 → Client）」与 `chat:deliver` 处理器设计。
- 删除：v1 第 11 章「下行链路同 Chat：Team → notify Map 实例 team:notify」设计。
- 删除：v1 遗留点 2「聊天上行走 Map 连接」备选方案——已由决策 B 关闭。
- 保留：`chat:locate` 思路演化为 `chat:region_players`（查询型，不投递）。

## 3. 配置驱动部署【决策 C】

### 3.1 deploy.yaml 契约（阶段 4 单机多进程示例）

```yaml
# demo/config/deploy.yaml —— 服务拓扑唯一事实源
redis:
  host: 127.0.0.1
  port: 6379

processes:
  social:                       # 低频接入/社交：默认合并部署单元
    services:
      - {type: gateway, count: 1, port: 8080}
      - {type: chat,    count: 1, port: 8081}
      - {type: team,    count: 1, port: 8082}
  map-1:
    services:
      - {type: map, mapId: map-1, channelId: ch-1, count: 1, port: 9001}
      - {type: map, mapId: map-1, channelId: ch-2, count: 1, port: 9002}
  map-2:
    services:
      - {type: map, mapId: map-2, channelId: ch-1, count: 1, port: 9011}
```

### 3.2 语义

- 每个 process 块 = 一个部署单元；services 列表声明该单元内的服务实例（type / count / 端口 / map 频道参数）。
- 低频服务默认合并 social；压力大时改 yaml（把 chat 挪到独立 process 块并给端口）即拆开，**代码不动**。
- 启动器 `demo/bin/launch.php`：解析 yaml → 逐 process 逐 service 生成 worker 启动命令（`php demo/bin/run-worker.php --service=gateway --port=8080 …`）并 spawn；阶段 4 不做进程监督/自动拉起（崩溃自愈靠注册表 TTL，进程拉起靠脚本，文档化）。
- 拆分验证是验收项：social 合并跑通 → 改 yaml 拆 chat → 再跑通（证明代码不动）。

## 5. 多频道模型（serviceType='map'）【决策 E】+ MAJOR-1 落点

### 5.1 serviceId 编码与 meta

- serviceType = `'map'`；serviceId = `{mapId}#{channelId}`（如 `map-1#ch-1`）。解析约定：以最后一个 `#` 切分；违反编码 → 防御性忽略该实例。
- meta 约定（demo 层协议）：`{mapId, channelId, playerCount, wsAddress}`。playerCount 由频道进程心跳携带更新；wsAddress 供 Gateway discover 后直接下发。
- discover('map') 返回全部存活频道实例；Gateway/Chat 按 `meta.mapId === 目标 mapId` 过滤。

### 5.2 进程与状态模型

- 每频道独立进程 + 独立 World，频道间零内存共享；单频道 count=1（单频道分片后置阶段 6）。
- playerCount 口径：本频道「已认证 Map 连接数」，onOpen/onClose 增减，心跳 Timer（5s）随 heartbeat 上报；新鲜度 ≤ 5s 心跳 + 15s TTL（软目标）。

### 5.3 MapServer 构造与启动（阶段 4 形态）

MapServer 构造新增注入：`string $serviceId`（如 `map-1#ch-1`）与 `string $mapId`（mapId 部分，供 MAJOR-1 比对；由 deploy.yaml 的 mapId/channelId 拼接而来）。onWorkerStart 顺序：register（含 meta）→ 心跳 Timer（带 playerCount）→ 组装 World → 按需建连对端；onWorkerStop → unregister。

### 5.4 MAJOR-1：mapId 校验落点与错误码（MINOR-R1 顺序修正）

落点 = MapServer 认证链路（handleAuth），**顺序为 peek → mapId 比对 → consume**：

```php
// MapServer::handleAuth 修订（MAJOR-1 + MINOR unauthorized 分支 + MINOR-R1 顺序）
$record = $this->tokenManager->peek($token);            // ① peek：读 uid / mapId / scopes（只读）

if ($record === null) {                                 // ② peek 不可见：无法比对 mapId，直接 consume 归因五态
    $status = $this->tokenManager->consume($token, 'map');
    $reason = match ($status) {
        TokenStatus::Expired      => 'expired',
        TokenStatus::Replayed     => 'replayed',
        TokenStatus::Unauthorized => 'unauthorized',    // MINOR：新增分支（scope 未授权）
        default                   => 'invalid',
    };
    $this->send($conn, Message::create('auth_failed', ['code' => 403, 'reason' => $reason], $message->requestId));
    $conn->close();
    return;
}

if ($record->mapId !== $this->mapId) {                  // ③ MAJOR-1：mapId 与本实例不符（不 consume）
    error_log(sprintf('[MapServer] mapId mismatch: token=%s uid=%s instance=%s',
        $record->mapId, $record->uid, $this->serviceId));   // 日志归因
    $this->send($conn, Message::create('auth_failed',
        ['code' => 403, 'reason' => 'map_mismatch'], $message->requestId));
    $conn->close();                                     // token 保留：'map' scope 未消费
    return;                                             // 客户端可拿该 token 重连正确频道正常认证
}

$status = $this->tokenManager->consume($token, 'map');  // ④ consume：五态判定并消费 'map' scope
if ($status !== TokenStatus::Valid) {
    $reason = match ($status) {
        TokenStatus::Expired      => 'expired',
        TokenStatus::Replayed     => 'replayed',
        TokenStatus::Unauthorized => 'unauthorized',
        default                   => 'invalid',
    };
    $this->send($conn, Message::create('auth_failed', ['code' => 403, 'reason' => $reason], $message->requestId));
    $conn->close();
    return;
}
// ⑤ 后续：建实体、AOI 登记、挂载 Actor、attach registry、auth_ok
```

要点：

- **顺序：peek → mapId 比对 → consume（MINOR-R1）**。理由：① mapId 比对必须基于 peek 的只读记录（consume 会先行消费 scope，比对须在消费前完成）；② **mapId 不符时不 consume**——token 保留、'map' scope 未消费，客户端拿该 token 重连正确频道即可正常 consume 认证（Valid），无需重新登录换 token。原 v2「consume 后比对 + 『token 已不可能再用于其它 Map 频道』」的注释为错误推论，已删除；③ 比对失败即断开，实体不挂载，无脏状态。
- peek 不可见（null）时无法比对 mapId → 直接 consume 归因五态（该路径 token 本就无效/过期/已重放，无需比对）。
- **防重放影响**：mapId 不符路径不 consume → 不写墓碑，重连正确频道后 consume 判 Valid，不产生 Replayed 误判。
- **错误码**：`auth_failed{code: 403, reason: 'map_mismatch'}`，与 reason 集合 `invalid | expired | replayed | unauthorized | map_mismatch` 统一（auth_failed 自此补 code 字段）。
- **日志归因**：`[MapServer] mapId mismatch: token={token.mapId} uid={uid} instance={serviceId}`——可用于发现「客户端拿旧 token 撞错频道 / Gateway 分配 bug」两类问题。

## 6. Chat 服务（对称直连版）【决策 B】

### 6.1 定位与状态

- serviceType = `'chat'`，serviceId = 逻辑实例 `'chat-1'`（social 拆分后不变）。
- 状态 = 玩家连接表：`uid → {conn, mapId, channelId, mapServiceId}`。连接认证时写入，断连删除。
- **连接表是唯一投递依据**；Map 的 uid 寻址（ServiceRegistry）仅用于**认证时获取 (mapId, channelId) 信息**——不用于投递判定。

### 6.2 认证流程

```
connect → auth{token}
  → peek(token) → null → auth_failed{403, invalid|expired} + 断开
  → consume(token, 'chat') → 非 Valid → auth_failed{403, invalid|expired|replayed|unauthorized} + 断开
  → resolve('map', uid) → serviceId（可 null）
  → 存连接表 uid → {conn, mapId: record.mapId, channelId: 解析自 serviceId 或 null, mapServiceId: serviceId|null}
  → auth_ok{uid}
```

resolve 为 null（Map 实例已死/映射过期，理论罕见）时**连接仍建立**：world/private 不受影响；channel/region 发言回 `chat:error{404, 'channel unknown'}`（可解释降级）。

### 6.3 消息类型与过滤语义（全对称直连）

上行 `chat:send{scope, content, mapId?, channelId?, targetUid?}`：

| scope | 过滤语义（投递全部走 Chat 自己的连接表） |
|---|---|
| `world` | 遍历连接表全量广播 `chat:message{scope:'world', content, fromUid}`；**跳过发送者本人连接**（MINOR-R8，与 region「跳过自己」一致；发送成功与否由错误回执承担，客户端本地回显自己的发言） |
| `channel` | 按连接表字段过滤：`conn.mapId === mapId && (channelId 缺省 || conn.channelId === channelId)`；**跳过发送者本人连接**（MINOR-R8）；无命中不报错（无人可收） |
| `region` | 见下方 region 分支 |
| `private` | 连接表查 targetUid → 命中定向发 `chat:message{scope:'private', …}`；**查不到 → `chat:error{404, 'target offline'}`**（对称直连下私聊 404 的依据是 Chat 连接表，不是 Map 寻址） |

**region 分支（MINOR 补全 + MINOR-R2 空区域判定）**：

```text
发送者 mapServiceId === null → chat:error{404, 'channel unknown'}（连接建立时 resolve 失败的降级）
call(map, mapServiceId, 'chat:region_players', {uid}) 超时 0.5s：
  → timeout / disconnected → chat:error{503, 'region unavailable'} + [cluster] 日志归因（可解释，发起方可重试）
  → ok 且 regionId === null → chat:error{404, 'region unknown'}（发送者不在线/无区域——MINOR-R2：以 regionId 判定，不再以 playerUids 空判定）
  → ok 且 regionId 非 null → 按 playerUids 过滤连接表定向发（跳过自己）
      玩家空投递：playerUids 为空 = 有区域但周围无人，正常完成、不报错（与 channel「无人可收」语义一致，MINOR-R2 消除 404 误报）
      playerUids 中的 uid 未在连接表 = 未连 Chat，自然跳过
```

Map 实例查询型 RPC（onRequest 处理器，替代 v1 的 chat:deliver/chat:locate）：

- `chat:region_players`（call）：{uid} → {regionId: ?string, playerUids: list\<string\>}。实现：registry 查 uid 对应 entity → AOI 九宫格 query → 邻居 entityId（`uid@connId` 格式）提取 uid 部分；**返回前 array_unique 去重（MINOR-R3：同 uid 多开两个 connId 会贡献重复 uid，契约承诺返回去重后的列表——去重落点固定在 Map 端，Chat 端信任契约、不再重复去重）**；uid 不在线 → {regionId: null, playerUids: []}。**只返回数据，不投递任何帧**。

### 6.4 依赖方向

Chat（demo 层）→ cluster（ServiceRegistry resolve/discover + RpcClient call）+ security（token 多 scope 认证）。Chat 不依赖 Map 具体实现（仅经 RPC 类型约定）；Map 不依赖 Chat；World 零依赖。

## 7. Team 服务（对称直连版）【决策 B】+ MAJOR-4/5/6

### 7.1 定位与状态

- serviceType = `'team'`，serviceId = `'team-1'`。队伍状态内存态（阶段 4 不持久化）。
- 玩家连接表：`uid → conn`（连接认证时写入，断连删除）。**所有下行通知走 Team 自己的连接**。
- 队伍模型：`teamId → {leaderUid, members: list<uid>, invites: list<{targetUid, invitedAt, expiresAt}>}`；`maxSize` 构造参数默认 5。
- **不再 resolve('map', targetUid) 做邀请投递**：「目标在线」= Team 连接表命中；不在线 → 404（对称直连口径，见 2.2 第 4 条）。

### 7.2 消息协议与回执（MAJOR-5：invite 双向回执）

上行（Client → Team）：`team:invite{targetUid}` / `team:accept{teamId}` / `team:reject{teamId}` / `team:leave{teamId}` / `team:disband{teamId}`。

下行：**成功一律 `team:ok{teamId, action}` 回发起方**（invite 成功回执即 MAJOR-5 要求）；失败一律 `team:error{code, message}`。通知帧（发全队或队长）：`team:notify{type: invited|joined|rejected|left|disbanded, teamId, uid, fromUid?}`，经 Team 连接表直发，uid 不在表 → 跳过并记日志（目标未连 Team 服务，可解释）。

回执方向总表（检查清单第 1 项依据）：

| 上行 | 发起方回执（成功/失败） | 通知对象（team:notify） |
|---|---|---|
| invite | team:ok{teamId} / 404·403·409·400 | 目标：invited |
| accept | team:ok / 404·403·409（team_full / already_in_team） | 全队：joined |
| reject | team:ok / 404·403 | 队长：rejected |
| leave（成员） | team:ok / 403 | 全队：left |
| leave（队长） | team:ok | 全队：disbanded（顺位继承后置，阶段 4 直接解散） |
| disband | team:ok / 403·404 | 全队：disbanded |

### 7.3 状态机边界矩阵（MAJOR-4/7 补全）

`team:invite{targetUid}`：

| 条件（按序判定） | 行为 |
|---|---|
| targetUid 缺失或 === 自己 | team:error{400} |
| 发送者无队伍 | 自动建队（leader=发送者）→ 继续 |
| 发送者是队长 | 继续（**队长已有队伍再邀请 = 正常邀请，不重复建队**） |
| 发送者是成员非队长 | team:error{403, 'not_leader'} |
| 目标已在任意队伍（members 命中） | team:error{409, 'target_in_team'} |
| members 数 ≥ maxSize | team:error{409, 'team_full'} |
| 目标未连 Team 服务（连接表未命中） | team:error{404, 'target_offline'} |
| 同 team 同 target 邀请已存在 | **幂等**：刷新 invites 条目 expiresAt = now+30s，重新回 team:ok + 重新 notify invited（客户端按 teamId 幂等去重） |
| 正常 | 写 invites（30s 过期）→ notify 目标 invited → team:ok{teamId} |

`team:accept{teamId}`（MAJOR-7：一 uid 一队不变量完备）：

| 条件（按序判定） | 行为 |
|---|---|
| 邀请不存在或已过期（>30s） | team:error{404, 'invite_not_found'} |
| 邀请 targetUid ≠ 自己 | team:error{403} |
| **自己在任意队伍（members 命中）** | **team:error{409, 'already_in_team'}（MAJOR-7：防「先后 accept 两邀请入两队」；Team 单进程串行处理请求，无并发竞态）** |
| 队伍不存在（accept 前已解散） | team:error{404, 'team_not_found'} |
| 满员（members ≥ maxSize，accept 前被别人填满） | team:error{409, 'team_full'} |
| 正常 | 入队 → 删该 invites 条目 → **清除该 uid 其余全部待处理 invites（遍历所有队伍，删除 targetUid === uid 的邀请条目；MAJOR-7 防御：接受一个邀请后，其余邀请全部失效）** → notify 全队 joined → team:ok |

> MAJOR-7 说明：`findTeamByUid(uid)` 命中任一队伍 members 即 409 拦截，保证「一 uid 一队」；「清除其余全部邀请」是写后防御（即使未来判定顺序调整或出现其它入队路径，残余邀请也不会在离队后复活生效）。两者共同使 7.4 的 findTeamByUid 结果不产生双队歧义。

`team:reject{teamId}`：邀请不存在 → 404 'invite_not_found'；targetUid ≠ 自己 → 403；正常 → 删邀请 → notify 队长 rejected → team:ok。

`team:leave{teamId}`：非成员 → 403 'not_member'；成员 → 退队 → notify 全队 left → team:ok；队长 → 解散 → notify 全队 disbanded → team:ok。

`team:disband{teamId}`：队伍不存在 → 404；非队长 → 403 'not_leader'；正常 → 解散 → notify 全队 disbanded → team:ok。

邀请过期清理：惰性判定（accept/reject 时查 expiresAt）+ Team 进程内 Timer（60s）周期移除过期 invites。

### 7.4 MAJOR-6：队长频道优先（取消「最近在线成员」）

Team 服务 RPC：`team:query_preferred_channel`（call）{uid, mapId} → {channelServiceId: ?string}：

```php
function queryPreferredChannel(string $uid, string $mapId): ?string {
    $team = $this->findTeamByUid($uid);          // uid 所在队伍（member 或 leader）
    if ($team === null) return null;             // 无队伍
    $svcId = $this->registry->resolve('map', $team->leaderUid);
    if ($svcId === null) return null;            // 队长无映射 / 所在实例已死（寻址自愈后自然为 null）
    [$leaderMapId] = explode('#', $svcId);       // serviceId 前缀解析（约定：最后 # 切分）
    return $leaderMapId === $mapId ? $svcId : null;   // 跨图不跟随
}
```

- **只查队长，无兜底链**（v1 的「队长 → 最近在线成员」删除）：队长不在线/无映射/跨图 → null → Gateway 降级最少在线。
- 依赖方向：Gateway → Team（RPC call）→ ServiceRegistry（resolve）；无循环。

## 8. token 多授权设计【决策 F】+ MAJOR-2 + MINOR

### 8.1 契约修订（MAJOR-2）

```php
// TokenRecord：{uid, mapId, scopes: list<string>, issuedAt, expiresAt}
// 构造签名：__construct(string $uid, string $mapId, array $scopes, float $issuedAt, float $expiresAt)

interface TokenManagerInterface
{
    /** scopes 由 Gateway 白名单过滤（仅 'map'/'chat'/'team' 子集，去重后非空），缺省全量 */
    public function issue(string $uid, string $mapId, array $scopes = ['map'], int $ttlSeconds = 30): string;
    /**
     * 五态一次性消费（MAJOR-2：带 scope）。
     * scope 白名单 /^[a-z][a-z0-9-]{0,31}$/：不匹配在管理器层短路为 Invalid，不进存储层
     * （scope 会进入 Redis 键构造，白名单收敛键注入面；store 层同规则二次校验）。
     */
    public function consume(string $token, string $scope): TokenStatus;
    /** 签名不变：只读返回含 scopes 的 TokenRecord（语义见 8.5） */
    public function peek(string $token): ?TokenRecord;
}

interface TokenStoreInterface
{
    public function save(string $token, TokenRecord $record, int $ttlSeconds): void;
    public function consume(string $token, string $scope): TokenStatus;   // MAJOR-2
    public function peek(string $token): ?TokenRecord;
    public function remove(string $token): void;
}

enum TokenStatus { case Valid; case Expired; case Replayed; case Invalid; case Unauthorized; }
```

### 8.2 防重放语义（主键保留 + per-scope 独立墓碑）

- 主键 `{prefix}{token}`（JSON 含 scopes）保留至 Redis TTL 兜底；per-scope 墓碑 `{prefix}{token}:consume:{scope}`（SETEX 至原 expiresAt）。
- 同一 scope 二次 consume → Replayed；不同 scope 互不影响。原总墓碑键 `:tombstone` 取消（阶段 4 无存量数据）。
- 五态语义：**Valid** = 该 scope 首次消费成功（写墓碑）；**Expired** = 主键存在但 expiresAt < now（DEL 主键，见 8.6）；**Replayed** = 该 scope 墓碑命中；**Invalid** = 主键不存在/格式非法/记录畸形；**Unauthorized** = token 有效但 scope 不在 scopes 列表（不消费任何标记，主键保留，客户端统一拒绝、服务端日志归因）。

### 8.3 各服务校验语义

- Map：consume(token, 'map') + mapId 比对（MAJOR-1）；Chat：consume(token, 'chat')；Team：consume(token, 'team')。任一服务只校验自己的 scope；重连重试同一 token → Replayed（客户端需重新登录）。

### 8.4 RedisTokenStore Lua 修订（含 MINOR：畸形 scopes 判 Invalid + DEL）

```lua
-- KEYS[1]=主键 KEYS[2]=scope 墓碑；ARGV[1]=now ARGV[2]=scope
-- 返回：0=valid 1=expired 2=replayed 3=invalid 4=unauthorized
local now = tonumber(ARGV[1])
local scope = ARGV[2]
if redis.call('EXISTS', KEYS[2]) == 1 then
    return 2                                    -- 该 scope 已消费：Replayed
end
local raw = redis.call('GET', KEYS[1])
if not raw then
    return 3                                    -- 主键不存在：Invalid
end
local ok, rec = pcall(cjson.decode, raw)
if not ok or type(rec) ~= 'table' or not rec.expiresAt then
    redis.call('DEL', KEYS[1])
    return 3                                    -- 主键畸形：Invalid + DEL（防畸形键反复触发）
end
local expiresAt = tonumber(rec.expiresAt)
if not expiresAt then
    redis.call('DEL', KEYS[1])
    return 3
end
if expiresAt < now then
    redis.call('DEL', KEYS[1])
    return 1                                    -- 过期：Expired（跨 scope 可见性见 8.6）
end
local authorized = false
if type(rec.scopes) == 'table' then
    for _, s in ipairs(rec.scopes) do
        if s == scope then authorized = true break end
    end
elseif rec.scopes == nil and scope == 'map' then
    authorized = true                           -- 向后兼容：旧格式（无 scopes）视为仅授权 'map'
else
    redis.call('DEL', KEYS[1])
    return 3                                    -- MINOR：scopes 存在但畸形类型 → Invalid + DEL（非 Unauthorized）
end
if not authorized then
    return 4                                    -- scope 未授权：Unauthorized（不消费任何标记，主键保留）
end
local remain = math.ceil(expiresAt - now)
if remain < 1 then remain = 1 end
redis.call('SETEX', KEYS[2], remain, '1')       -- 写 per-scope 墓碑，主键保留
return 0
```

save：主键 JSON 增加 scopes 字段。remove 简化：DEL 主键（per-scope 墓碑各自 TTL 自然消亡，继续防「已消费 scope 重放」；主键删除后未消费 scope → Invalid，撤销语义正确）。peek：读主键返回含 scopes 的 TokenRecord。

### 8.5 MINOR：peek 语义漂移 docblock 声明

v1 墓碑模型下「已消费 → peek null」；per-scope 墓碑模型下主键保留，**peek 只基于主键可见性**：主键存在且未过期即返回含 scopes 的 record，与 per-scope 墓碑无关。TokenStoreInterface::peek 与两个实现的 docblock 必须改写为：「只读查看（不消费）：主键存在且未过期 → 返回含 scopes 的记录；主键缺失/畸形/已过期 → null。**不感知 per-scope 消费墓碑**（某 scope 已消费后 peek 仍返回 record）」。调用方（三服务的 auth 链路）顺序为 peek → consume；**Map 例外：peek → mapId 比对 → consume（5.4，MINOR-R1）**，语义不受影响。

### 8.6 MINOR：Expired DEL 主键的跨 scope 可见性文档化

Expired 判定时 Lua DEL 主键：**首个撞上过期判定的 consume（任意 scope）返回 Expired 并删除主键；其余 scope 再 consume → 主键不存在 → Invalid**。即 Expired 是「一次性可见」——token 生命周期已终结，后续 scope 得 Invalid 属可解释语义（客户端一律重新登录），文档化于 RedisTokenStore/InMemoryTokenStore docblock 与测试矩阵（对拍两实现）。

### 8.7 InMemoryTokenStore 同步扩展

墓碑表键改为 `"{token}:{scope}"`；consume(token, scope) 五态逻辑、scope 白名单、scopes 畸形/旧格式兼容与 Redis 版逐条对齐（测试对拍）。

## 9. Gateway 登录与频道分配【决策 G】+ MINOR

### 9.1 时序

```text
Client                Gateway                          Redis                       Team 服务
  │ login{uid,mapId,scopes?}  │                          │                            │
  ├──────────────────────────►│ authenticate → uid       │                            │
  │                           │ ① call team:query_preferred_channel{uid,mapId}（超时 0.5s，同步）
  │                           ├──────────────────────────────────────────────────────────►│
  │                           │◄─── ok{channelServiceId|null} / timeout / disconnected ────┤
  │                           │    timeout|disconnected|null → 降级（日志归因）
  │                           │ ② discover('map') → map<serviceId, ServiceInstance>，按 meta.mapId 过滤
  │                           │ ③ 选频道：preferred 存活且在过滤结果内 → 用之；否则 min(meta.playerCount)
  │                           │    过滤结果为空 → login_failed{503}
│                           │ ④ bind('map', uid, serviceId)（MAJOR-3：按实例分组键，TTL 6h）
│                           │ ⑤ issue(uid, mapId, scopes=白名单过滤后的 ['map','chat','team'])
│                           │    issue 失败 → unbind('map', uid, serviceId) 回滚 + login_failed{500}
│                           │    （MINOR-R5：不留「有映射无 token」的残留，resolve 不被污染）
│                           │ ⑥ discover('chat')/'team' → 两地址（空 → null 缺省）
  │◄─ login_ok{token, map:{wsAddress}, chat:{wsAddress}|null, team:{wsAddress}|null} ─┤
  │                           │（此后 Client 分别直连 map/chat/team，各 consume 对应 scope；Gateway 连接断开）
```

### 9.2 分配伪代码（discover map 契约 + RpcStatus enum）

```php
function assignChannel(string $uid, string $mapId, ?array $requestedScopes): AssignResult {
    // ① 队长频道优先（同步 call，阻塞本 worker ≤0.5s——见 9.5）
    $preferred = null;
    $r = $this->rpc->call('team', $this->teamServiceId, 'team:query_preferred_channel',
                          ['uid' => $uid, 'mapId' => $mapId], 0.5);
    if ($r->status() === RpcStatus::Ok && is_string($r->payload()['channelServiceId'] ?? null)) {
        $preferred = $r->payload()['channelServiceId'];
    }   // Timeout/Disconnected → 日志归因后走默认均衡（登录不失败）

    // ② discover('map')：array<string, ServiceInstance>（MINOR：map 契约），心跳存活已过滤
    $channels = array_filter($this->registry->discover('map'),
        fn($i) => ($i->meta['mapId'] ?? null) === $mapId);
    if ($channels === []) return AssignResult::failed(503, 'no available channel');

    // ③ 最少在线均衡 + 队长优先例外
    $target = ($preferred !== null && isset($channels[$preferred]))
        ? $channels[$preferred]
        : min_by($channels, fn($i) => (int)($i->meta['playerCount'] ?? PHP_INT_MAX));

    // ④ ⑤ ⑥（MINOR-R5：issue 失败必须 unbind 回滚，不留 uid 映射残留）
    $this->registry->bind('map', $uid, $target->id);
    try {
        $token = $this->tokens->issue($uid, $mapId, $this->filterScopes($requestedScopes));
    } catch (\Throwable $e) {
        $this->registry->unbind('map', $uid, $target->id);   // 回滚：否则 resolve 指向一个客户端永不会连上的频道
        return AssignResult::failed(500, 'token issue failed');
    }
    return AssignResult::ok($target->meta['wsAddress'], $token);
}
```

**虚映射降级路径（MINOR-R5）**：bind 成功但客户端最终未连该 Map 频道（issue 成功但客户端丢弃 token / 断网 / 崩溃）时，uid 映射成为「虚映射」。各消费方均可解释：① Chat 认证 resolve 命中 → 连接表 mapId/channelId 按分配记录（channel 发言过滤正常，与本人是否真连了 Map 无关）；② region 发言 → region_players 查不到 entity → {regionId: null} → 404 'region unknown'（可解释，6.3）；③ Team 队长优先 → 按 bind 语义返回频道（「已分配」≠「已连上」，文档化；playerCount 不含未认证玩家，均衡不受虚映射影响）；④ 虚映射不依赖 Map 实例存活：实例心跳过期即退出 resolve 范围（10.3 自愈），6h TTL 兜底清理。无脏状态、无需额外清理。

### 9.3 scopes 签发来源（关闭 v1 遗留点 1）

login payload 可请求 scopes + 服务端白名单过滤（仅 map/chat/team 子集，去重非空），**缺省全量**。已裁决，不再待确认。

### 9.4 MINOR：login_ok 空地址缺省字段

login_ok 固定四字段：`{token, map:{wsAddress}, chat:{wsAddress}|null, team:{wsAddress}|null}`。discover('chat')/'team' 为空 → 对应字段 null，客户端禁用对应功能（登录不失败）；map 为空 → login_failed{503}（地图是核心）。客户端无需处理缺字段。

### 9.5 MINOR：登录 0.5s 阻塞 call 文档化

Gateway 登录 handler 内的 `team:query_preferred_channel` 为同步 call，阻塞当前 worker 事件循环 ≤0.5s（超时上限）；Gateway 多 worker 各自独立阻塞；登录低频（每玩家一次）可容忍。若阶段 5 压力升高 → RpcClient 增加异步 call 变体（后置，不进本阶段契约）。

### 10.1 跨服 TCP + RPC（含 MINOR：RpcStatus enum）

```php
namespace Nythros\Network;
interface RemoteTransportInterface
{
    public function connect(string $address): void;   // 已连接为幂等 no-op
    public function onConnect(callable $handler): void;
    public function onMessage(callable $handler): void;   // (string $payload)
    public function onClose(callable $handler): void;
    public function send(string $payload): bool;      // 未连接返回 false（调用方丢弃 + 日志，不抛异常）
    public function isConnected(): bool;
    public function close(): void;
}

namespace Nythros\Cluster;
enum RpcStatus { case Ok; case Timeout; case Disconnected; }   // MINOR：string → enum

interface RpcClientInterface
{
    /** 永不抛异常，超时/断连以 RpcStatus 返回 */
    public function call(string $serviceType, string $targetId, string $type, array $payload = [], float $timeoutSeconds = 5.0): RpcResultInterface;
    public function notify(string $serviceType, string $targetId, string $type, array $payload = []): void;
    public function onRequest(string $type, callable $handler): void;
}

interface RpcResultInterface
{
    /** Ok = 已处理且响应到达；Timeout = 已发送未确认（at-least-once）；Disconnected = 未发送 */
    public function status(): RpcStatus;
    public function payload(): array;
    public function error(): ?string;
}
```

实现 `SimpleRpcClient`：per-request 单调 requestId + 等待表 + 100ms 超时扫描 + ServiceRegistry 寻址 + RemoteTransport 传输；对端处理器异常回 rpc:error 帧。`WorkermanAsyncTcpTransport`（network-workerman，包装 AsyncTcpConnection；不内置重连）。

### 10.2 ServiceRegistry（含 MINOR：discover map 契约）

```php
namespace Nythros\Cluster;
interface ServiceRegistryInterface
{
    public function register(string $serviceType, string $serviceId, array $meta = []): void;   // 重复注册 = 覆盖 meta + 续心跳（自愈路径）
    public function heartbeat(string $serviceType, string $serviceId, array $meta = []): void;  // 5s/15s；meta 原子合并（playerCount 上报）
    /** @return array<string, ServiceInstance> map<serviceId, ServiceInstance>（MINOR：统一 map 契约） */
    public function discover(string $serviceType): array;    // 弱一致快照，至多 TTL 延迟；心跳键缺失即不可见
    public function unregister(string $serviceType, string $serviceId): void;
    public function resolve(string $serviceType, string $uid): ?string;   // uid → 存活实例 id；无映射返回 null
    public function bind(string $serviceType, string $uid, string $serviceId, int $ttlSeconds = 21600): void;
    public function unbind(string $serviceType, string $uid, string $serviceId): void;
}
final readonly class ServiceInstance { public string $id; public array $meta; }
```

### 10.3 MAJOR-3：uid 映射按实例分组 + 自愈

**键设计（修订）**：

- `nythros:svc:{type}` = hash `{serviceId => JSON meta}`
- `nythros:svc:hb:{type}:{serviceId}` = SETEX（TTL 15s）
- `nythros:svc:uid:{type}:{serviceId}` = hash `{uid => '1'}`，EXPIRE 21600s（**每次 bind 续期**）

**语义**：

- `bind`：HSET 该实例 hash + EXPIRE 续期（覆盖写 = 同 uid 后登录者覆盖先登录者，会话期 TTL 与 token TTL 解耦）。
- `unbind`：HDEL 该实例 hash 的 uid 字段——**键按实例分组后，「仅当当前映射值等于 serviceId 才删」的条件删除语义天然成立**（跨实例误删不可能）。unbind 有两处用途：① Map 断连清理；② Gateway 登录链路 issue 失败时的回滚（MINOR-R5，见 9.1/9.2）。
- `resolve`：discover(type) 得存活实例列表 → **按 serviceId 字典序（ksort 后）逐实例 HGET uid hash** → 首个命中返回 serviceId → 全 miss → null。O(存活频道数)，可接受。**多实例命中确定性（MINOR-R4）**：同 uid 多开 bind 在多个频道时，字典序取首个——语义确定且稳定，不随 hash 遍历顺序漂移；该结果只用于寻址判定（在线/频道归属），**不保证与用户「最后登录/最近活动」频道一致**（已文档化，消费方不得依赖该排序表达偏好）。
- **自愈链路**：实例心跳过期（15s）→ discover 不可见 → 该实例的 uid hash 自动退出 resolve 查询范围（**uid 寻址随注册表自愈，无需依赖 6h TTL**）；discover 惰性 HDEL 死实例时顺带 DEL 其 uid hash 键（空间回收）。
- **验收补充**：kill -9 Map 频道进程 → ≤15s 后：discover('map') 不含该实例、resolve 该频道玩家 uid 为 null（私聊 404 / 组队邀请 404 / 队长优先降级）、重启恢复后新登录玩家重新 bind。

### 10.4 ActorRef（不变，保留 v1）

ActorRefInterface / ClusterRouterInterface：LocalActorRef（tell → EventBus 信封）、RemoteActorRef（持有 serviceType/serviceId/actorId，tell → RpcClient notify，payload 附 actorId）、ClusterRouter（本地查 actorSystem，远端查 ServiceRegistry::resolve）。依赖：cluster → contracts + network + protocol。**注**：ActorRef 是服务间业务投递（Map→Map 等），与客户端下行无关，对称直连不影响本节。

### 10.5 persistence（不变，保留 v1）

StorageInterface（save/load/delete/saveBatch 返回失败 id 列表）+ RepositoryInterface；InMemoryStorage + MySqlStorage（PDO 单表 upsert）；ArchivePipeline（demo 组装层）：标脏 → 断连/登出立即 flush → 30s 定时兜底批量 saveBatch，失败重试超限记日志放弃。MySQL 为本阶段可裁剪项。

### 10.6 多进程（钳制移除）

## 15. 检查清单 6 项自检（终版，覆盖全部设计）

1. **数据流方向对称性**：① token：issue（Gateway 写）↔ 三服务 consume(scope)（消费）↔ per-scope 墓碑（防重放），五态覆盖全部结果，Unauthorized/畸形 scopes/Expired 跨 scope 均给语义；Map 例外链路 peek → mapId 比对 → consume（不符不消费，token 保留可重连，MINOR-R1）；② uid 映射：bind（Gateway 写，issue 失败 unbind 回滚 MINOR-R5）↔ resolve（Chat 认证取 map/channel、Team 队长寻址读，多实例命中字典序确定 MINOR-R4）↔ unbind（Map 断连 HDEL，分组键天然条件删除）↔ 实例心跳过期整体失效（MAJOR-3 自愈）；③ 频道：register/heartbeat(playerCount) ↔ discover ↔ 心跳过期自愈；④ 聊天：上行 Chat 直连 ↔ 下行 Chat 直连（同一连接对称），world/channel/region 统一跳过发送者本人（MINOR-R8），私聊 404 回执、region 404（regionId null，MINOR-R2）/503 回执——发起方永远知道自己消息的结局；⑤ 组队：每操作有发起方回执（team:ok/team:error，MAJOR-5）与通知对象（全队/队长/目标）双向闭环；accept 补「自己在任意队伍 → 409 already_in_team」+ 入队后清除其余全部邀请（MAJOR-7），「一 uid 一队」不变量在 invite 侧（409 target_in_team）与 accept 侧（409 already_in_team）双向拦截；⑥ 登录：login_ok 三地址固定字段（null 缺省，MINOR）。核对无遗漏。
2. **接口契约完整性**：上层需用的能力逐一进入契约——SchedulerInterface(+addTaskToRegion)、RemoteTransportInterface、RpcClientInterface+RpcStatus、ServiceRegistryInterface(bind/unbind/resolve，MAJOR-3 键语义)、ActorRef 族、Storage 族、TokenStoreInterface::consume(token, scope)（MAJOR-2）；Map 的 chat:region_players、Team 的 query_preferred_channel 为 demo 层协议经 RpcClient::onRequest 泛化接口承载，不进 contracts（与「具体消息类型不进契约」先例一致）。无 instanceof 收窄剩余。核对通过。
3. **返回值语义一致性**：consume 五态每态一句话定义且两个 store 对拍；discover 统一 map\<serviceId, ServiceInstance\>（Gateway 按 id 取实例 O(1)，MINOR）；resolve 返回 ?string（null = 无存活实例映射，Chat 降级受限连接、Team 队长寻址降级、Gateway 降级最少在线三处消费方语义一致；多实例命中按 serviceId 字典序取首个，确定性语义 MINOR-R4）；RpcResultInterface::status 为 RpcStatus enum 三值互斥（MINOR）；region_players 返回 {regionId:?string, playerUids:[]} 与 Chat 404/503 分支一一对应；saveBatch 失败列表语义与归档重试一致。逐项核对通过。
4. **时序/延迟语义**：登录链路 = authenticate + Team 同步 call ≤0.5s（worker 阻塞，文档化 9.5）+ discover + bind + issue + 下发，正常 O(10ms)、故障 ≤0.5s 有界降级；聊天 = 连接表遍历帧外直发 + region 一次 call ≤0.5s（Chat 进程阻塞，低频可容忍）；组队全本地 O(1)；playerCount 新鲜度 ≤20s（5s 心跳 + 15s TTL）；uid 映射断连 HDEL 即时、kill -9 自愈 ≤15s（MAJOR-3）；归档丢失窗口 ≤30s（断连必写）；RPC 超时判定 [t, t+0.1s]。消费方均可容忍。
5. **边界条件覆盖**：同 uid 多开（Map entityId=uid@connId 多开共存；Chat/Team 连接表覆盖写=后连接收消息，文档化；bind 覆盖写 + 分组 unbind 不误删）；**Team accept 双队（MAJOR-7：accept 时自己在任意队伍 → 409 already_in_team，Team 单进程串行处理请求无 TOCTOU；入队后清除该 uid 其余全部邀请——「一 uid 一队」不变量完备，findTeamByUid 无双队歧义）**；token 全 scope 消费后主键保留（Redis TTL 清理）；同 scope 重放 Replayed；未授权 scope Unauthorized；旧格式 token 兼容 ['map']；scopes 畸形类型 Invalid + DEL（MINOR）；Expired 跨 scope 可见性（MINOR 8.6）；mapId 不符 → 403 map_mismatch 且不 consume（token 保留可重连正确频道，MINOR-R1）；无存活频道 → 503；队长频道已死/跨图/队长无映射 → 降级最少在线（MAJOR-6）；Chat 认证时 resolve null → 受限连接（channel/region 404）；region 发送者无区域（regionId null）→ 404、有区域但邻居空 → 正常完成不报错（MINOR-R2）、locate 超时 → 503；world/channel 跳过发送者本人（MINOR-R8）；bind 后 issue 失败 → unbind 回滚、虚映射降级可解释（MINOR-R5）；Team 满员/目标已组队/已解散/邀请过期/重复邀请幂等刷新（MAJOR-4）；Team 重启队伍丢失（文档化）；kill -9 → 注册 + uid 寻址双自愈（MAJOR-3）；重复 register 同 id → 覆盖 meta 续心跳；Redis 不可用 → throw 不 exit。逐项有预期行为。
6. **铁律对照**：World 零新增依赖（四服务 + 分配全部在 demo 组装层 + cluster 包）；不为未来堆功能（无聊天历史/队伍持久化/单频道分片/重发队列/进程监督——分机演进只做零成本约束声明，不写代码，决策 D）；先单机正确性（全部同机多进程验证，一进程一实例为性能隔离决策，与铁律方向一致）；每个核心模块有测试（token 五态矩阵、Registry 分组键 + 双自愈集成、RPC 超时、Chat 四语义、Team 状态机边界矩阵、Gateway 分配矩阵、deploy.yaml 拆分验证）。

## 16. 风险与开放问题

- Chat/Team 同 uid 多开：连接表覆盖写（后连接收消息），与 Map 多开共存语义不同，已文档化；若需「全部连接都收」改 uid→conn[] 即可，不进本阶段。
- region 发言一次同步 call 阻塞 Chat 进程 ≤0.5s：低频可容忍；**验收补 Benchmark 测量「region 发言期间并发 world/private 消息延迟」并记录数据（MINOR-R7，见 18 章）**；阶段 5 高频化可改异步 call 或 Map 实例上行代发（后置）。
- uid hash 键 6h TTL：死实例键至多 6h 后被 Redis 清理（discover 惰性 DEL 加速回收）；resolve 正确性不依赖该 TTL（以 discover 存活为前提）。
- social 合并**已裁决「部署单元口径」**（一启动脚本 + master + 三 Worker 各自端口）——这是 Workerman 模型下对「一个服务进程」意图的工程化实现（共享启停生命周期 + 进程内可优化）；严格单 OS 进程单端口需单端口多协议分发，复杂度另计，本 ADR 明确不取（MINOR-R6），不再保留待确认。
- Team 队伍状态内存态：重启丢失，重新组队（文档化）。
- 跨服通道复用 WebSocket 端口 + JSON：阶段 6 跨机前 Benchmark 评估专用内部端口。
- 参数（心跳 5s/15s、RPC 超时 5s、登录期 0.5s、uid 映射 TTL 6h、归档 30s、邀请 30s、maxSize 5、限流）为默认值，验收时可调，非架构决策。
- v1 遗留点 3/4/5 沿用结论：region 粒度 = AOI cell 九宫格（参数化可调）；同 uid 多开后登录覆盖寻址不顶号；Chat/Team 单实例口径；mapId 来自 login payload 服务端白名单校验（未知 mapId → 400）。遗留点 2/7 已被本版关闭（对称直连 B / scopes 签发 9.3）。

## 18. 验收口径（终版）

- 多频道：map-1#ch-1 / map-1#ch-2 / map-2#ch-1 三进程并存，discover('map') 全量可见 + mapId 过滤正确；playerCount 心跳周期内更新；最少在线分配可观测。
- 队长频道优先（MAJOR-6）：A 登录 ch-1 → B 组队后登录 → B 进 ch-1；杀 Team 服务 → 降级最少在线（日志归因）；队长所在实例被 kill -9 → ≤15s 后降级最少在线。
- token：三服务各 consume 同 token 各 Valid；同 scope 重放 Replayed；未授权 Unauthorized；过期 Expired；remove 后未消费 scope Invalid；scopes 畸形 → Invalid + 主键 DEL；Expired 跨 scope 可见性符合 8.6。
- **mapId 校验（MAJOR-1，MINOR-R1 顺序）**：token.mapId 与频道不符 → auth_failed{403, map_mismatch} + 日志归因，且 **'map' scope 未消费**（随后拿同 token 重连正确频道 → consume 判 Valid，正常进图）；相符正常进图。
- **uid 寻址自愈（MAJOR-3）**：kill -9 频道进程 → ≤15s 后 resolve 该频道玩家 uid = null（私聊 404 / 组队邀请 404）；重启恢复后重新 bind 可寻址。
- Chat（对称直连）：world 全表可收、发送者本人不重复收；channel 只达目标 map/channel（发送者本人跳过）；region 只达发送者所在频道同 cell（经 region_players，发送者本人跳过；MINOR-R8 三 scope 统一跳过自己）；region 发送者有区域但邻居空 → 正常完成不报错（MINOR-R2）；private 达目标（对方在 Chat 连接表）；目标未连 Chat → 404；region 发送者无区域 → 404；region 定位超时 → 503。
- Team（MAJOR-4/5/7）：invite 成功发起方收 team:ok{teamId}、目标收 invited；边界矩阵逐条（403/409/404/幂等刷新）；accept→joined 全队可见；reject 只通知队长；leave/disband 语义正确；满员 accept 409；**双队防护（MAJOR-7）**：C 无队收 A、B 两邀请 → accept(A) 入 A 队后 30s 内 accept(B) → **404 invite_not_found**（B 的 C 邀请已在入队时被防御性清除，accept 的邀请条目判定 ① 先于 ③ 命中）；**409 already_in_team 仅在「幂等刷新重发邀请」或「清除失效」等防御路径触发**（该分支的防护价值是写后防御，不承担主场景判定）；A/B 两队 members 与 invites 中 C 均不重复。
- **region 阻塞 Benchmark（MINOR-R7）**：测量同 Chat 进程内 region 发言（一次同步 call ≤0.5s）期间的并发 world/private 消息延迟（p50/p99），与无 region call 基线对拍，数据记录入复盘文档；若延迟显著恶化，触发 9.5 的异步 call 变体评估（后置决策，不在本阶段实现）。
- 部署（决策 C）：social 合并启动 → deploy.yaml 拆 chat → 重跑通过（代码零改动）。
- 原有验收保留：注册表自愈、跨服业务消息、断线窗口对账、persistence 归档。
