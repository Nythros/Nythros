# ADR-019：包拆分与发布形态（engine 物理合并 + MIT 许可证）

> 状态：已接受（阶段 6 决策，已裁决）。
> 关联：ADR-018（阶段 6 发布与生态规划，其中决策 1「包发布粒度」的最终落地）、ADR-016（framework 与 Demo 方向）、ADR-017（framework 层设计）、blueprint `07-阶段实现清单.md`（阶段 6 任务与门禁）。

## 1. 决策

- **包拆分方式**：物理合并——15 个核心包（contracts/kernel/kernel-workerman/scheduler/world/entity/actor/aoi/event/network/network-workerman/protocol/security/persistence/cluster）代码合并为单包 `nythros/engine`；`nythros/framework` 保持独立；`nythros/demo` 作为 create-project 模板雏形（独立仓库后置）。
- **namespace 策略**：保留 15 个 namespace（`Nythros\Contracts\`、`Nythros\Kernel\` 等）不统一，源码零改动。理由：包间运行时耦合已收敛到 contracts 接口 + workerman 绑定类，合并只动 composer.json 与目录，不动源码。
- **许可证**：MIT（开源默认，蓝图未定，阶段 6 先行确定）。
- **版本**：`v0.1.0-alpha` 起步（API 已冻结）。

## 2. 理由

- 弃方案 1（engine meta 包）：需 15 包先上 Packagist + 15 组 tag 同步，且 15 内部包无独立消费者，收益为零。
- 弃方案 3（整仓发布）：违反 Engine/Framework 分离铁律。
- 选物理合并：用户安装心智是「一个 engine + 一个 framework」，15 内部包边界不应暴露给最终用户。

## 3. 依赖关系（合并后）

- `nythros/engine` require `workerman/workerman ^5.2.2`（kernel-workerman/network-workerman 原本就 require）。
- `nythros/framework` require `nythros/engine`（原 contracts + actor）。
- `nythros/demo` require `nythros/engine` + `nythros/framework` + `workerman/gateway-worker ^4.0.1`（social 层）。

## 4. 待人工配合项（后置）

- GitHub/Gitee 仓库、Packagist 注册、真实 create-project 验证——均需人工，阶段 6 内跳过，仅准备配置。

## 5. 发布管线落地（2026-09-02 实施，决策 B = subsplit）

发布时决定「composer 走完整 subsplit + Packagist，npm 暂缓」。技术根因：**Packagist 只读仓库根
`composer.json`**，monorepo 子包（`packages/engine` 等）的 composer.json 在子目录 → 必须 subsplit
到独立仓（`Nythros/engine`、`Nythros/framework`）才能被 Packagist 识别为 `nythros/engine`。

落地改动（`.github/workflows/release.yml` 重写为四段流水线，v* tag 触发）：

1. **release**：phpunit + phpstan 门禁 → `composer archive` 打 engine/framework zip → GitHub Release。
   此段**永不因发布 secret 缺失而失败**（zip 是保底分发物）。
2. **subsplit**（`if: secrets.SUBSPLIT_TOKEN != ''`）：`git subtree split` 按矩阵把两包拆到各自
   独立仓，强推 `main` + 同名版本 tag。未配 token 时整段跳过（渐进启用）。
3. **packagist**（依赖 subsplit + `secrets.PACKAGIST_TOKEN`）：`POST /api/update-package` 显式刷新
   两包版本；与拆分仓后台配的 GitHub webhook 幂等共存（双保险，二选一即可）。
4. **npm**（`if: secrets.NPM_TOKEN != ''`）：现状 org 未建 → 不配 secret 即跳过，不阻塞前三段。

**版本约束的连带修正**（发布前必须，否则 subsplit 出去的包依赖链断裂）：
- monorepo 三处内部依赖从 `@dev` 改为 `^0.1`（framework→engine、demo→engine+framework、
  根 composer→三包），使 engine 独立发布后 framework 能解析到正式版；
- 采用 **path repository `options.versions` 注入 `0.1.x-dev`** 而非在子包 composer.json 写 `version`
  字段——后者被 `composer validate` 判为反 Packagist 惯例（应用 tag 定版）。此法令 monorepo 开发期
  内部解析不断（`^0.1` 命中 `0.1.x-dev`），拆分仓则纯靠 tag 定版。

**人工前置清单**（决策 B 生效需你完成）：

| # | 动作 | 产出 |
|---|---|---|
| 1 | 建空仓 `Nythros/engine`、`Nythros/framework`（GitHub；**不勾 README/gitignore**，首推由 CI 完成） | subsplit 目标 |
| 2 | 生成有 Contents:write 的 fine-grained PAT → 存为 monorepo secret `SUBSPLIT_TOKEN` | 解锁 subsplit job |
| 3 | Packagist 用 GitHub 登录注册 `nythros/engine`/`framework`，仓库地址填**拆分仓**；配 webhook 或存 `PACKAGIST_USERNAME`+`PACKAGIST_TOKEN` secret | 解锁 packagist job |
| 4 | （可选，npm 暂缓时跳过）npmjs 建 `@nythros` org + 存 `NPM_TOKEN` secret。包版本已就位（package.json `0.1.0`，ProtocolVocabulary 守卫 phpunit 绿），配好 token 即解锁 | 解锁 npm job |

配置端全部就绪后，`git push github master --follow-tags`（或单独推 `v0.1.0`）即触发。第 1–3 步
完成前推 tag，CI 也只跑 release 段出 zip，**不会红**。
