# 分层审计报告（engine / framework / demo）

> 审计方法：以「机制 vs 玩法」判别法（换游戏类型是否仍存在 + 是否含业务名词 + 依赖方向）系统扫描三包，
> 找出可上提/下沉/待澄清/应删除的代码。结论供制定下一步演进方向，不构成立即重构指令。
> Audited by the mechanism-vs-gameplay discriminator (would it exist in another game genre + does it name a
> business concept + dependency direction). Results guide the next evolution; this is not a mandate to refactor now.

## 1. 总体现状：层级很健康

| 检查项 | 结果 |
|---|---|
| 引擎 import 业务（demo/framework/Social） | 零（引擎无任何业务依赖） |
| 框架 import demo | 零 |
| 引擎类名/接口名含业务词（Monster/Drop/Skill/Player/Quest...） | 零 |
| 框架四基类依赖 | 只 extends 引擎 BaseActor + 本层 Damageable |
| World/AOI/EventBus/协议 接口实现数 | 全部 >=1 实现（无未实现契约） |

核心结论：当前的「实现先于抽象」演进模式执行得干净——引擎里没有业务残余，demo 是唯一的业务面。下面的发现全是「何时/是否上提」的时机判断，不是「位置错误」。

## 2. 可上提候选（demo → 引擎/框架：机制级，等待第二次消费者）

判别标准：零业务名词 + 依赖全是引擎接口 + 换游戏类型仍存在。但当前都只有 MapServer 一个消费者——按三次法则，第二次消费者出现前上提属过早抽象。

| 候选 | 定位 | 依赖面 | 上提建议 |
|---|---|---|---|
| FrameMerger（帧合并：去重/优先级/批量） | 机制级（网络出站优化，与游戏无关） | engine ConnectionInterface / BatchSerializerInterface | 已「半个引擎化」——它消费的 BatchSerializerInterface 已在引擎；FrameMerger 自身仍在 demo。第二个需要批量出站压缩的业务出现时，上提到 engine/src/Network/ |
| ConnectionRegistry（连接<->实体双映表） | 机制级（连接与实体的关联是通用网络+实体模型） | engine ConnectionInterface / EntityInterface 概念（当前未直接依赖，只存字符串 id） | 同上。依赖已抽象（只存字符串 id），上提几乎是搬文件 |
| PerfSampler（探针->Redis） | 机制级（运行期观测是通用能力） | demo 无；依赖 engine PerfProbe | PerfProbe 已在引擎，Sampler 是它的 Redis 落地方。第二个服务类型需要采样时提为 engine/src/Telemetry/ |
| Identity（userId+username 值对象） | 机制级（身份是安全层概念） | engine IdentityInterface | 建议立即上提：它只是 IdentityInterface 的普通实现，引擎安全层已有 TokenRecord/TokenStatus 等值对象，Identity 放 demo 属于「实现放错目录」——引擎 Security/ 应有它的位置 |
| StaticAuthenticator（静态账号认证） | 机制级（认证器） | engine AuthenticatorInterface | 仅 demo 用（gateway-worker 装配）。若将来开放注册，此认证器会被通用化；否则可留 demo |

## 3. 框架层定位审查（framework 是否含纯玩法？）

| 类 | 现状 | 判定 |
|---|---|---|
| BasePlayer / BaseMonster / BaseNPC | 框架四基类 | 合理：通用角色骨架（状态机/实体绑定）是框架能力；攻击/掉落等玩法在 demo Combat/* |
| Plugin/Skill|Item|Buff | 框架插件区 | 边界张力：Skill/Item/Buff 是「泛游戏数值插件」的雏形——框架层可保留（作为插件机制官方数据示例），但不要把 demo 战斗规则（冷却公式、掉落表）搬进插件。插件的度=「提供数据注册/查询 API」，玩法度=「结算规则」 |
| Damageable | 框架契约 | 合理（战斗语义的通用抽象） |

## 4. 应删除：引擎死接口

- engine/src/Persistence/RepositoryInterface.php：零实现、零调用（find/persist/remove/findBy 无任何消费者；InMemoryStorage/MySqlStorage 走 StorageInterface）。建议删除——这是曾设计未用、违反 YAGNI 的残留，正是「过早抽象」的反面教材。

## 5. 待澄清 / 演进观察点

- VisionBroadcasterInterface（demo/Combat）：语义上是机制级（「广播给一组连接」），但因签名带 entityId/payload 通用形状而暂居 demo。它其实是 broadcastToAll 的天然宿主——本次 2a 的 broadcastToAll 方案放在它身上合适（继续留 demo，等第二个战斗消费者再上提）。
- 副本编排（dungeon 分类/两级选择/DungeonWorldPool）：全部 demo（运营编排）。不要下沉到引擎——引擎保留 WorldType 机制，编排永远在业务层。

## 6. 给 AI 协作的分层口诀（防之后再污染）

1. 命名错位即红线：引擎文件出现 Monster/Drop/Skill/Quest 命名 → 停止，这是玩法泄漏。
2. 「换游戏类型会变吗」：会 → 玩法层；不会 → 机制层。
3. 三次法则：一个消费者 = 留在当前层；两个消费者 = 提层；三个 = 必须提层。
4. 引擎接口窄化：只为真实调用加方法；加方法就是承诺，删不掉。
5. 孤儿即删：引擎里任何无实现/无调用的接口类 → 删（YAGNI）。
